1. 概述与架构设计

1.1 项目背景

CGC Engine 是基于 llama.cpp 的 MoE (Mixture of Experts) 专家缓存推理优化引擎，核心目标是在资源受限的边缘设备上实现大参数 MoE 模型的高吞吐推理。

核心设计理念：A3B 模型每 token 仅激活 top-8/256 专家（约 3B 参数），但跨 token 的累计 working set 远大于此。Expert Cache 池根据 routing mass 分布动态调整，而非加载全部 35B 参数。

1.2 跨平台架构

层级职责跨平台抽象
应用层llama-server / API 服务HTTP 标准协议，全平台通用
推理层llama.cpp 核心推理C++ 标准，全平台通用
专家缓存层CGC Expert Cache (DBUF/SPAC)C++ 标准，全平台通用
计算后端层GPU 加速Metal (Mac) / CUDA (Win/Linux) / Vulkan (通用) / ROCm (AMD)
系统层内存管理/线程/文件IOpthread (Mac/Linux) / Win32 (Windows) / POSIX
关键洞察：CGC Expert Cache 的核心逻辑（DBUF、SPAC、EMA 估计器、Down-Combine）是纯 C++ 实现，不依赖任何平台特定 API。移植的主要工作集中在 GPU 计算后端和系统层适配。

3. 三方合并策略（跨平台代码整合）

3.1 为什么需要三方合并

CGC Engine 的开发分布在多个代码仓库和分支中：

  • Mac 开发分支（devserver）：包含完整的 Expert Cache、DBUF、SPAC、Down-Combine 实现，基于 Metal 后端
  • 跨平台 fork 分支（cgcengine0907）：包含 Vulkan/Windows 适配修改，基于上游 llama.cpp
  • 上游基线（ggml-org/llama.cpp）：官方 llama.cpp 主分支

三方合并的目标是将 Mac 分支的 Expert Cache 优化与跨平台 fork 的 Vulkan/Windows 适配整合到同一个代码库中。

3.2 三方合并模型

          base (07fdd66 - 共同祖先)
         /    \
        /      \
   ours        theirs
   (fork)      (Mac HEAD)
   Vulkan/     Expert Cache/
   Windows     DBUF/SPAC/
   适配        Down-Combine
        \      /
         \    /

3.3 核心文件合并清单

只针对核心 5+2 个文件做逐文件三方合并，避免混入大量临时文件和无关变更。

优先级文件Mac 侧变更fork 侧变更合并复杂度
⭐⭐⭐llama-expert-cache.cpp651 行（完整实现）无（新文件）低（直接带入）
⭐⭐⭐llama-expert-cache.h201 行（数据结构）58 行（Option 定义）中（Option 合并）
⭐⭐⭐llama-context.cpp818 行（DBUF/SPAC 注入）228 行（Vulkan 适配）高（冲突区域多）
⭐⭐llama-graph.cpp47 行（Down-Combine 分支）13 行（MoE 构建）中
⭐⭐ggml-backend.cpp109 行（专家权重加载）68 行（后端注册）中
⭐llama-context.h少量（接口声明）21 行（Vulkan 接口）低
⭐llama.cpp少量（Option 解析）87 行（CLI 参数）低

3.4 合并执行步骤

1
准备三个版本的文件 
# base（共同祖先）
git show 07fdd66:src/llama.cpp/src/llama-context.cpp > /tmp/base_context.cpp

# ours（fork 分支，含 Vulkan/Windows 适配）
git show fork HEAD:src/llama.cpp/src/llama-context.cpp > /tmp/ours_context.cpp

# theirs（Mac HEAD，含 Expert Cache）
git show mac HEAD:src/llama.cpp/src/llama-context.cpp > /tmp/theirs_context.cpp
2
执行三方合并 
# 使用 git merge-file 自动合并
git merge-file /tmp/ours_context.cpp /tmp/base_context.cpp /tmp/theirs_context.cpp

# 检查冲突标记
grep -n "<<<<<<<\|=======\|>>>>>>>" /tmp/ours_context.cpp
3
手动解决冲突

冲突主要集中在 llama-context.cpp 的以下区域：

  • 专家缓存初始化：Mac 侧添加了 expert_cache_init() 调用，fork 侧可能有不同的初始化顺序
  • decode 循环：Mac 侧添加了 DBUF/SPAC 的 hook 注入点，fork 侧可能有 Vulkan 同步调用
  • 内存管理：Mac 侧使用 Metal 统一内存，fork 侧使用 Vulkan 设备内存
4
验证合并结果 
# 编译验证
cmake -B build -DGGML_VULKAN=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --target llama-server -j8

# 功能验证（3 Profile 质量测试）
python3 scripts/check/replay_server_profile.py --profile coding --runs 3
python3 scripts/check/replay_server_profile.py --profile qa-zh --runs 3
python3 scripts/check/replay_server_profile.py --profile longform-zh --runs 3
重要提醒：合并过程中不要清理构建产物（build/ 目录、*.dylib/*.dll/*.so）。之前的经验表明，清理产物后可能无法重建，导致重大损失。保留构建产物可以随时回滚和验证。

Windows 移植注意事项

CUDA 后端专家缓存位置：CUDA 后端的专家缓存池位于 GPU 显存中，而非系统内存。8GB pool 需要 GPU 有至少 10GB 显存（模型权重 + pool + KV cache）。如果显存不足，使用 Vulkan 后端或减小 pool 大小。
  • 文件路径：Windows 使用反斜杠 \，在代码中使用 / 或 \\
  • 线程模型：Windows 使用 Win32 线程，llama.cpp 已抽象为 ggml_thread
  • 动态库：Windows 使用 .dll，确保所有依赖 DLL 在 PATH 中或与 exe 同目录
  • 内存映射：Windows 的 MapViewOfFile 与 macOS 的 mmap 行为略有差异，专家权重加载可能需要调整
  • Down-Combine：CUDA 版本的 Down-Combine kernel 尚未实现，需要从 Metal 版本移植（约 300 行 CUDA C++）

Linux 移植注意事项

  • 多 GPU 支持：Linux 支持多 GPU 张量并行，使用 --tensor-split 参数分配
  • NUMA 架构：多 socket 服务器需要注意 NUMA 绑定，使用 numactl

  • Down-Combine：CUDA 版本需要移植，ROCm 版本可基于 CUDA 版本转换（HIPIFY）
  • 专家缓存：CUDA 后端 pool 在 GPU 显存；CPU 后端 pool 在系统内存

7. HarmonyOS 平台移植指南

HarmonyOS 平台概述

HarmonyOS 是面向鸿蒙生态的移植目标，包括 PC（Kirin 9030 + Maleoon 935）和手机端。目前处于原型阶段，使用 Vulkan GPU 后端或 CPU 推理。

硬件要求（HarmonyOS PC）

组件配置
CPUKirin 9030 8核 (2.75 GHz)
GPUMaleoon 935 (Vulkan 1.3)
内存16GB+ (带宽 ~44 GB/s)
后端CPU-only (Vulkan 驱动开发中)
预期性能3-5 t/s (Qwen3.6 IQ3_XXS)

构建与部署

# 1. 在 Linux 交叉编译环境中构建
cd deploy-harmonyos/harmonyos
./build.sh

# 2. 部署到 HarmonyOS 设备
cd ..
./deploy-to-harmonyos.sh user@device-ip

# 3. 在设备上运行
./harmonyos/run.sh -m model.gguf

HarmonyOS 移植挑战

  • Vulkan 驱动：Maleoon GPU 的 Vulkan 驱动尚在完善，部分扩展可能不支持
  • 内存带宽：~44 GB/s 远低于 Mac M4 的 546 GB/s，是性能瓶颈
  • 专家缓存：CPU 后端 pool 在系统内存，需要优化预取策略
  • Down-Combine：Vulkan 版本 kernel 尚未实现

8.3 严格 A/B 测试协议

验证优化效果时，使用严格的 A/B 交替测试排除机器状态干扰：

  1. 相同 prompt、相同 max_tokens（如 coding 固定 512 tokens）
  2. 交替执行（A = 无优化, B = 有优化, A, B...）
  3. 固定 Seed=42
  4. 对比 steady decode tps（去掉前 50 tokens 的 warmup）
  5. 每次测试前 kill 残留 server，确保干净启动
  6. 关闭其他应用，释放内存，减少机器波动

9. 常见问题与解决方案

9.1 构建问题

Q: CMake 找不到 CUDA / Vulkan

A：确保已安装对应 SDK，并设置环境变量：

# CUDA
export CUDA_HOME=/usr/local/cuda
export PATH=$CUDA_HOME/bin:$PATH

# Vulkan
export VULKAN_SDK=/path/to/vulkan-sdk

Q: 编译时报专家缓存相关错误

A：检查是否正确合并了核心文件。确保以下文件存在且包含 CGC Expert Cache 代码：

  • src/llama-expert-cache.cpp / .h
  • src/llama-context.cpp（包含 DBUF/SPAC 注入点）
  • src/llama-graph.cpp（包含 Down-Combine 分支）

9.2 运行时问题

Q: 启动时 OOM (Out of Memory)

A：减小 Expert Cache Pool 大小或使用更低比特量化：

# 减小 pool 到 4GB
export CGC_SERVER_EXPERT_CACHE_BYTES=4294967296

# 或使用 OOM 安全模式
export CGC_SERVER_OOM_SAFE=1

Q: MTP 模式下 server 崩溃

A：确保设置了 CGC_NO_PREFETCH=1。MTP+OA_ASYNC + 背景 pool fill 会导致 mid-decode 崩溃，这是已知的架构限制。

Q: 质量退化（输出循环/重复）

A：检查以下几点：

  1. 是否启用了 renorm（CGC_RN_ROUTING=1）？renorm 会导致质量退化，应保持关闭
  2. Expert Cache Pool 是否太小？pool 太小导致 cold miss 率高，影响质量
  3. 是否在干净的机器状态下测试？内存压力会导致质量波动

9.3 性能问题

Q: decode tps 远低于预期

A：按以下顺序排查：

  1. GPU 利用率：使用 nvidia-smi (CUDA) 或 Metal System Trace (Mac) 检查 GPU 利用率
  2. 专家缓存命中率：检查 server 日志中的 cold miss 率，目标 < 10%
  3. 内存带宽：专家权重从磁盘加载时受 IO 限制，确保模型在 SSD/NVMe 上
  4. 量化格式：IQ3_XXS 反量化开销较大，Q3_K 可能更快

Q: draft_accept 率低（< 90%）

A：draft_accept 低通常意味着 draft model 与 trunk model 的输出差异大。检查：

  • MTP draft model 是否正确加载？
  • 是否启用了影响输出的优化（如 renorm、fast-path-wait）？
  • 温度/top-p 等采样参数是否一致？

9.4 跨平台特定问题

Q: Windows 下专家权重加载慢

A：Windows 的内存映射（MapViewOfFile）可能比 macOS 的 mmap 慢。可以尝试：

  • 使用 --mmap 参数显式启用内存映射
  • 将模型文件放在 NTFS 压缩关闭的分区
  • 禁用 Windows Defender 实时扫描（仅对模型目录）

Q: Linux 多 GPU 下专家缓存分布不均

A：使用 --tensor-split 参数手动分配各 GPU 的权重比例，确保专家缓存池均匀分布。

Q: HarmonyOS 下 Vulkan 后端初始化失败

A：Maleoon GPU 的 Vulkan 驱动可能不支持某些扩展。尝试：

  • 使用 CPU-only 后端（-ngl 0）
  • 更新到最新的 HarmonyOS GPU 驱动
  • 检查 Vulkan 支持的扩展列表：vulkaninfo | grep extension
