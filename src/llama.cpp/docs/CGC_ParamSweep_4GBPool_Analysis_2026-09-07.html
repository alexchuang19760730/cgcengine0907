1. 执行摘要

核心结论 1：6 个可调参数（SPAC_ALPHA / SPAC_K / SPAC_REFRESH / DBUF_CAP / MMV_NSG / PREFETCH_WINDOW）全部扫描完成，默认值/已调优值已经是最优。当前生产配置达到 25.87 t/s（中位数）/ 26.19 t/s（最佳），3/3 质量达标，超过 25+ 目标。
核心结论 2：4GB Pool 理论上可行，但需要 MTP Draft Prefetch 预测准确率 ≥ 90%（临界值），≥ 95% 完全无损。MTP draft 预计能达到 93-95%，刚好超过临界值。
核心结论 3：4GB Pool 的最大障碍不是预测准确率，而是 MTP+OA_ASYNC + 背景 pool fill 的崩溃问题（已知架构限制）。需要先实现 safe async fill window，才能验证 4GB + draft prefetch 的实际效果。

2.3 各参数详细分析

SPAC_ALPHA (EMA 衰减系数)

11 点细扫（0.5, 0.55, 0.6, 0.65, 0.7, 0.725, 0.75, 0.775, 0.8, 0.85, 0.9）确认 α=0.75 为最优。α 过小导致 EMA 跟踪太慢，α 过大导致 EMA 太敏感、噪声大。

K=12 虽然最稳定但速度慢，因为预取过多专家导致 pool churn 增加。K=4 波动大，因为预取不足导致 cold miss 增加。K=8 是速度和稳定性的最佳平衡点。

REFRESH=1（每步都 refresh）是最优的，因为 MoE routing 变化快，需要及时更新 EMA 估计器。增大 refresh 间隔会导致跟踪滞后，cold miss 增加。

4. 4GB Pool 可行性深度分析

4.1 容量对比

Pool 大小Slots/layer质量覆盖率 (coding)实测速度状态
8GB~71~76%25.87 t/s✅ 生产验证
4GB~35~50% (估算)8.82 t/s❌ 无 prefetch 时失败
6GB~53~65% (估算)未测试🔄 待验证

4GB pool 的 slots 是 8GB 的一半，之前测试失败（8.82 t/s，只输出 3 tokens）是因为 没有 prefetch，cold miss 率太高。

4.2 MTP Draft Prefetch 的原理

当前 token decode
    ↓
MTP draft 预测 next N tokens
    ↓
每个预测 token 激活 top-8 experts
    ↓
提前把这些 experts 加载到 pool (prefetch)
    ↓
next token decode 时这些 experts 已经 resident
    ↓
cold miss 率大幅降低 → 小 pool 也能保持高速度
关键洞察：每个 token 只激活 8 个 experts，如果 prefetch 能准确预测这 8 个，pool 只需要容纳：
  • 当前 token 的 8 个 active experts
  • 下一步预测的 8 个 experts（prefetch）
  • 少量历史 warm experts（LRU 保留）
理论最小 pool：~16-24 slots/layer ≈ 2-3GB，4GB 绰绰有余。

5. MTP Draft Prefetch 预测准确率临界值

5.1 预测准确率与 Cold Miss 的关系

预测准确率 每 token cold miss 数 8 experts 中 resident 数 预期影响 评级
100% 0 8/8 速度无损 ✅ 完美
95% 0.4 7.6/8 几乎无损 ✅ 优秀
90% 0.8 7.2/8 轻微开销 ⚠️ 临界
85% 1.2 6.8/8 可感知减速 ⚠️ 较差
80% 1.6 6.4/8 明显减速 ❌ 不达标
70% 2.4 5.6/8 严重减速 ❌ 失败
临界值：≥ 90% 准确率可以保持速度基本无损；≥ 95% 完全无损。低于 90% 会有可感知的减速。

5.2 实际能达到的准确率

预测来源准确率说明
相邻 token routing 重叠~87%step-to-step stability（代码注释中的测量值）
MTP draft token accept~96%当前生产配置的 draft_accept_pct
MTP draft expert routing~93-95% (估算)draft token 被接受 → 其 expert routing 也正确
EMA 估计器 (SPAC)~85-90%α=0.75 的 EMA 预测准确率
结论：MTP draft prefetch 的预测准确率预计在 93-95%，刚好超过 90% 的临界值，理论上可以用 4GB pool 保持速度和精度无损。

5.3 但实际还需要解决的问题

问题说明难度优先级
MTP+OA_ASYNC + 背景 pool fill 崩溃 已知架构限制，CGC_NO_PREFETCH=1 是必须的 🔴 高 P0
Async fill 安全窗口 需要在 verify/draft 之间插入 GPU idle barrier 🟡 中 P0
Draft ctx 的 routing 捕获 MTP draft ctx 的 expert_cache_on_topk 需要 feed 到 prefetch 🟡 中 P1
4GB pool 的 LRU churn pool 小 → 淘汰频繁 → warm experts 被过早 evict 🟡 中 P1
Cold miss 的加载延迟 从磁盘加载专家权重 ~1-3ms/expert，0.8 miss/token 可接受 🟢 低 P2
最大障碍：不是预测准确率，而是 MTP+OA_ASYNC + 背景 pool fill 的崩溃问题。需要先实现 safe async fill window，才能验证 4GB + draft prefetch 的实际效果。

6. 下一步实现路线图

6.1 推荐路线（按优先级排序）

1
P3 批量同步（+3-5%，风险低，2-3h）
  • 合并多层 ids 读 + remap 写，减少 CPU-GPU 同步次数
  • 风险低，收益稳定，先做这个提升基线速度
  • 目标：从 25.87 → 26.5-27 t/s
2
Safe Async Fill Window（解锁 4GB pool 的关键，中-高风险，3-4h）
  • 在 verify 和 draft 之间插入 GPU idle barrier
  • 只 fill 非 union slots，避免 race condition
  • slot double-buffering 防止读写冲突
  • 这是 P1 (GPU slot mapping kernel) 的前置条件
  • 目标：解锁 MTP 路径下的背景 pool fill
3
4GB + Draft Prefetch A/B 验证（验证 4GB 可行性，1-2h）
  • 4GB pool + CGC_NO_PREFETCH=0 + draft prefetch
  • 测量 residency、cold miss rate、decode t/s、质量
  • 对比 8GB pool 基线
  • 目标：验证 4GB pool 能否达到 25+ t/s 且质量无损
4
P2 GEMV Coalescing 优化（+3-8%，中风险，2-3h）
  • 优化 MoE GEMV 的内存访问模式，提升 coalescing
  • 目标：进一步提升 decode 速度
5
P1 GPU Slot Mapping Kernel（+5-8%，中-高风险，3-4h）
  • GPU 端 slot 映射 kernel，减少 CPU-GPU 同步
  • 依赖 safe async fill window 先实现
  • 目标：最终速度突破 28-30 t/s
