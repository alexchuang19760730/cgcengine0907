1. 架构概述

CGC (CGC Engine) Expert Cache 是一套针对 MoE (Mixture of Experts) 模型的专家权重缓存与推理优化系统，核心目标是在资源受限的边缘设备（如 16GB M4 Max MacBook）上运行大参数 MoE 模型时，通过智能缓存、预取和计算融合，实现高吞吐推理。

1.1 核心设计理念

Working Set 原理

A3B 模型每 token 仅激活 top-8/256 专家（约 3B 参数），但跨 token 的累计 working set 远大于此。Expert Cache 池的大小根据 routing mass 分布动态调整，而非加载全部 35B 参数。

分层缓存架构

L4 slot pool 作为 GPU 端的专家权重缓存，配合 LRU 淘汰、EMA 效用估计、异步预取和 step-ahead refill，最大化 resident expert 比例，减少文件 I/O。

3. 环境变量 Option 全览

重要：run_server.sh 使用 env "${SERVER_ENV[@]}" "$BIN" 启动 server，不继承外部 shell 环境变量。每个 CGC_* 变量必须显式添加到 SERVER_ENV 数组才能传递给 server 进程。

3.1 核心缓存配置

Option默认值说明状态
CGC_SERVER_EXPERT_CACHE_BYTES0（禁用）Expert Cache 池大小（字节）。生产配置：8GB = 8589934592。决定每层可缓存的 expert slot 数量。生产

3.2 DBUF (Double Buffer) - Step-Ahead Refill

Option默认值说明状态
CGC_DBUF未设置（OFF）启用 hook-time step-ahead refill。在 per-layer GPU-idle hook 窗口，将当前 step 的 ZERO-mapped cold union 成员加入 prefetch 队列，让 next step 找到它们 resident。生产配置：启用生产
CGC_DBUF_CAP24prefetch 队列容量上限。防止 early-decode cold burst（12/layer × 41 layers ≈ 500 fills）超出 ~40ms step 窗口。生产

3.3 SPAC (Spatial Activated Estimator) - EMA 效用估计

Option默认值说明状态
CGC_SPAC未设置（OFF）启用 EMA 效用估计器。per-(layer, expert) EMA utility，utility[L][e] = α·u + (1−α)·routed。用于 prefetch 目标选择和 EMA-biased 淘汰。生产配置：启用生产
CGC_SPAC_ALPHA0.75（已调优）EMA 衰减系数 α。范围 0~1。α 越大，越重视近期 routing；α 越小，越平滑。细扫描结果：0.75 为最佳（中位数 25.87 t/s，最佳 26.19）。生产
CGC_SPAC_K8每次 refresh 预取的 top-K expert 数量。默认 OFF
CGC_SPAC_REFRESH未设置EMA top-K → prefetch 的刷新间隔（token 数）。默认 OFF
CGC_SPAC_DBG未设置SPAC 调试输出。调试

3.4 P0 Down-Combine (实验性)

Option默认值说明状态
CGC_DOWN_COMBINE未设置（OFF）启用 batch down-combine kernel。将 8 个 per-expert down GEMV + 7 次 add 合并为 1 个 kernel，减少 kernel launch 开销。仅支持 decode（n_tokens==1）、Q3_K down weights、无 scale/bias。实验
P0 测试结果（2026-09-07）：启用 CGC_DOWN_COMBINE=1 后，decode_tps 中位数 23.29，最佳 25.09（vs baseline 25.87），draft_accept 94.25%，质量 3/3 = 1.0。距离 25+ 目标只差 7%。

3.5 Prefetch 与 Prewarm

Option默认值说明状态
CGC_NO_PREFETCH未设置（prefetch ON）禁用背景预取。注意：MTP 生产配置必须设置此变量（0000 防护），因为 MTP+OA_ASYNC + 背景 pool fill 会导致 mid-decode 崩溃。生产
CGC_NO_PREWARM未设置（prewarm ON）禁用启动时的 prewarm（按 prefill route frequency 填充 top-K per layer）。默认 OFF
CGC_PREFETCH_SRC未设置预取源选择：step-union / EMA / draft look-ahead。默认 OFF
CGC_PREFETCH_WINDOW未设置预取滑动窗口大小。默认 OFF

3.6 已弃用 Option（不要使用）

Option弃用原因
CGC_DBUF2完整双缓冲 active/scratch 指针原子切换。6GB/8GB 反而慢 40-48%。
CGC_FAST_WAIT等待 in-flight fill 而非 ZERO-mapping。decode 慢 29-48%。
CGC_MMV_FUSEGLU 融合（gate+up+GLU）。平均 15.94 t/s（vs 基线 22.07），draft accept 暴跌。
CGC_RN_ROUTINGRenorm routing（排除非 resident expert）。质量 0.3 counting loop，NOOP bisect 确认 exclusion 是杀手。
CGC_WCOLD_ENWarm cold expert 处理。与 renorm 配合使用，已随 renorm 弃用。

4.1 测试基准：3 Profile 质量评估

质量评估使用三个标准化 profile，每个 profile 有明确的质量基线（baseline score）：

ProfileBaseline 质量内容类型说明
qa-zh1.0中文问答事实性、准确性、完整性
longform-zh0.882中文长文生成连贯性、结构、深度
coding1.0代码生成语法正确性、逻辑正确性、可运行性
质量判定标准：任何优化必须保持 3 个 profile 的质量不低于 baseline。coding profile 对数值扰动极其敏感（IQ3_XXS 量化下），即使 0.3 的退化也视为失败。

4.3 严格 A/B 测试协议

为排除机器状态干扰，验证优化效果时使用严格的 A/B 交替测试协议：

  1. 相同 prompt、相同 max_tokens（如 coding 固定 512 tokens）
  2. 交替执行（A = 无优化, B = 有优化, A, B...）排除机器状态干扰
  3. 固定 Seed=42
  4. 对比 steady decode tps（去掉前 50 tokens 的 warmup）
  5. 每次测试前 kill 残留 llama-server，确保干净启动
  6. 关闭其他应用，释放内存，减少机器波动

6. P0 Down-Combine 最新进展

6.1 设计目标

参考 Perplexity Lily 推理引擎的 moe_gather_gemv_q4_down_combine，将 MoE FFN 的 down projection 从"8 个 per-expert GEMV + 7 次 add"改为"1 个 batch combine kernel"，减少 kernel launch 开销。

6.2 开发过程中的关键发现

发现 1：模型实际量化格式不是 IQ3_XXS

模型文件名虽叫 ...IQ3_XXS-denseIQ4X.gguf，但实际 expert 权重是：

  • down_proj.exps: Q3_K (type=11)
  • gate/up_proj.exps: Q2_K (type=10)

导致最初的 IQ3_XXS 版本 kernel 条件检查永远失败，down-combine 从未真正启用。

发现 2：run_server.sh 不继承外部环境变量

run_server.sh 使用 env "${SERVER_ENV[@]}" "$BIN" 启动，env 会替换当前环境而不是追加。必须显式把每个 CGC_* 变量添加到 SERVER_ENV 数组。

发现 3：Metal backend 不支持 down-combine op（最严重）

ggml_metal_device_supports_op 函数只支持 MUL_MAT 和 MUL_MAT_ID，没有 MUL_MAT_ID_DOWN_COMBINE。导致 Metal backend 静默回退到 CPU，性能只有 6 t/s。

修复了三个地方：supports_op、get_op_batch_size、h_safe。

发现 4：nsg = -1 bug（性能杀手）

ggml_metal_nsg_env(GGML_TYPE_Q3_K) 返回 -1，因为 switch 语句中只有 IQ2_S 和 IQ3_XXS，没有 Q3_K。导致 grid 维度计算错误，性能只有正常的 40%（10.35 t/s）。

修复：使用 N_SG_Q3_K=2 常量。修复后性能飙升到 23.29 t/s。

6.4 下一步优化方向

  1. 并行度提升：当前总 threadgroup 数 513（z=1），原始 kernel 4104（z=8，每 expert 独立 threadgroup）。可考虑将 expert 循环移到 grid 维度 + reduction。
  2. nsg 参数调优：当前 nsg=2（官方默认），可尝试 nsg=1 增加 threadgroup 数量。
  3. 内存访问优化：检查 expert 间的权重读取是否有合并优化空间。
  4. 稳定性提升：3 次运行中有 1 次异常慢（7.89 t/s），需排查机器状态波动。

7. 未来方向

7.1 短期（1-2 周）

  • P0 Down-Combine 并行度优化，目标稳定 25+ t/s
  • P1：MoE routing 移到 GPU，减少 CPU-GPU 同步（参考 Lily），预期 +5-15%
  • P3：批量同步优化，减少 kernel launch 之间的 barrier 开销

7.2 中期（1-2 月）

  • 鸿蒙系统移植：所有 CGC_* option 设计为可配置，便于跨平台迁移
  • 32GB 硬件验证：更大 pool（128-192 slots/layer）下的质量-速度平衡点
  • Gated DeltaNet 层 Apple GPU 专项优化（如果模型包含），预期 +10-20%

  • 多模型 MoT (Model-on-Transfer) 端云协同：云端 DeepSeek V4 Flash 负责 Prefill+Speculative Draft，端侧 Qwen3.6-35B-A3B 仅执行 Verify

  • CGC Engine 商业化：仓储 AGV 与具身智能场景的边缘推理部署
