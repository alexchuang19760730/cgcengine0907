## §EN-419（2026-09-22 00:35）：「做一個跨硬體／跨模型自適應的 AI compiler」可行性裁決

使用者問：「建立跨硬體、跨模型自適應 backend 的 AI compiler 真的做不到嗎？看你完全沒頭緒」。
⇒ **不是做不到，是「做得到但動不到我們實測到的那面牆」，且通用版的成本比極差。**
（純分析，0 重建、0 量測。）

### 三層切分（所有後續討論用這套）
| 層 | compiler 動得到？ | 實測上限 |
|---|---|---|
| ① 圖層／排程（融合、砍 dispatch、重排 segment） | ✅ | **只 ~1%**（dispatch 固定成本 18.6 µs × 102 = 1.9 ms，佔 GPU busy ~1%） |
| ② kernel 效率（MoE matmul 的 tile／gather 局部性／dequant） | ✅ | **唯一可能的 1.345×**（有效頻寬 25 → 33.5 GB/s），即第 ③ 步的 revised kernel，P 10–20% |
| ③ 物理屋頂 + 容量／IO（25 GB/s 有效頻寬、1.189 GB/step、專家不進 RAM） | ❌ | **compiler 動不了** |

### 三條「compiler 也救不了」的理由（往後別再繞）
1. **屋頂線**：compiler 只能在 roofline 以下找，抬不高 roofline。25 t/s 要 33.5 GB/s；
   若實測有效頻寬已接近硬體可達值 ⇒ ② 也一起死（**這正是第 ② 步要先量的原因**）。
2. **依賴不可預知**：下一層用哪些專家，要等前一層算完才知道 ⇒ 預取窗口是**結構性 0**（L3 實測
   MoE 永遠在 segment 第一個 buffer），不是「排程寫得笨」。重排也變不出來。
3. **容量**：expert cache 存在是因為模型裝不進 RAM／GPU ⇒ 屬 **runtime 記憶體管理**，
   不在任何 compiler 的 IR 裡（TVM／IREE／XLA 都假設權重在記憶體中）。這是本 fork 的差異點，
   通用 compiler 反而會把它丟掉。

### 成本現實
- 通用 codegen（MLIR／IREE／TVM 路線）：要重寫全部 GGUF K-quant dequant（Q2_K…Q6_K、IQ 系），
  **12–24 人月起點只是追平手寫 GGML Metal kernel**，且 Metal 後端在這些框架裡偏弱。
- 狹義 autotuner（單一 op 家族 + microbenchmark 適應度）：**天到週**，是唯一有實測 upside 的。
- ⚠ 適應度函數要分開看：**端到端 t/s 不能當搜尋目標**（CV 7.88%，測 1.7% 效應要 165 臂）；
  但**單 kernel 的 GB/s microbenchmark 又快又低噪音** ⇒ autotune 方法學上在本機可行，
  卡的是物理不是方法學。

### 裁決／建議
- 若目標是「這台機器 25 t/s」⇒ compiler 是錯的工具，先做第 ② 步量有效頻寬（它同時是 compiler
  決策的前置）。
- 若目標是「可移植推理資產」⇒ 做 **形狀驅動的自適應調度表**（按 shape 查表選 tile／segment／
  backend），不是通用 codegen；backend 抽象層複用手寫 kernel，不要自己 codegen。

  （thermal 是 NOMINAL，usable 只在起跑前量一次、跑起來就變了）。

  ① **purge 有效於「可用」**：free 0.07 → **7.3 GB**、usable 7.9% → **48.6–52.6%**。

  只有關掉持有它的 app 或重開機才會降 ⇒ 門禁不能寫「swap==0」，否則永遠拒絕。
