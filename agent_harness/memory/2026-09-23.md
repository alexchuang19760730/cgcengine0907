⇒ 改兩處：**換預測源** ＋ **改成逐層在自己窗口內提前**。
⚠ 真門檻是**整層 union 全覆蓋**：U=10、p=0.87 獨立 ⇒ `0.87^10 ≈ 25%` ⇒ **pred 要比 top-8 寬**。

### 設計（階段 0 先量，不先改行為）
- **安全不變量**：快路徑條件是「**真 ids 全部 resident**」，不是「預測對了就跳過」
  —— 預測只決定提前填什麼，不決定相不信任結果。
- 硬約束（註解原文）：必須等**整段**跑完才能讀 ids ⇒ 並行的只能是 IO／填池，**不能是讀 ids**。
- 計數器 `CGC-PREBIND: calls/fast/slow/pred/cov/...`：**`calls==0` 這一輪無效**（F2 教訓）。
- 門檻事先寫死：`all_cov_layers / n_routable < 0.5` ⇒ 停在階段 0，改走 `pread_usec`。

### ★ 主指標用 `gap` 不用 t/s ⇒ 比 k 認證便宜一個數量級
`gap` 是 step 級計數器（一支 log 1300+ 樣本，**不需跨 launch 配對**）；
t/s 是 launch 級、單臂 sd 18%、要 8 對 ABBA。
判準：`gap_B/gap_A ≤ 0.60` 且 `fast/(fast+slow) ≥ 0.50` 且 `slow_us_B ≤ cb_A×1.10` 且 M1/M2/M3 9/9。

### 預期與邊界
快路徑全覆蓋 ⇒ `gap 59.0 → ~21.3` ⇒ `total 183.5 → ~141.4`（**−23%**）⇒ t/s 約 **+30%**。
⚠ **與既有天花板衝突**（L3 誠實上界 ~+7% ⇒ 13.5）：衝突來源很可能是**天花板假設了
CPU 必須在關鍵路徑**，而本設計正是在拆那個假設 ⇒ 有實測前不當承諾，也不拿它推翻 L3。

### 未解（別當成已解決）
① **截距 +7.2 ms 是否 ∝ 段數：無法用既有 log 判定** —— 這批 log 只有 `segs ∈ {2, 41}`
   兩種值，**沒有中間點可回歸**（`segs=2` 的 `union 11.3 > total 1.6`，口徑不同，不可用）。
② ntok=4 斷崖是 hook 次數變多（推算 ~4 → ~15 次/step）還是每次變貴？**沒有逐層計數器**。
③ `ensure_batch` 2.267 ms/call 是全程平均（含 warmup），穩態值未分離。
④ union 大小只有兩個取樣點（ntok=1 → 8 ids；ntok=8 → ≥16，且 `CGC-HOOK` 截斷在 16）。

## §EN-458 預指派定價：我第一版模型的方向錯了（續 §EN-457）

使用者給了 A（預指派）／B（slot 間接化）／C（提高容量）／D（攤薄）四點判斷，
全部同意方向，並補了「命中率是關鍵、F2 的 null 不能否決 A」。我重算後**發現自己
§EN-457 的模型有一個方向性錯誤**，且糾正後結論反轉。
新工具 `scripts/check/prebind_ev.py`（selftest **27/27**）；長文
`docs/PREBIND_TRADEOFF_2026-09-23.md`；`PREBIND_SLOT_DESIGN_2026-09-23.md` 加更正橫幅。

### ★★ 錯誤：`f_clean` 不是 `q^U`，是 `r^U`，而 `r = p_res0 + (1-p_res0)*q`
基線已有 85% 的被選專家常駐（`llama-context.cpp:5380`「15% non-resident」）；預指派
**不是從零建立常駐，只救那 15% 冷的**。我第一版把「被預測覆蓋」當成 resident 的唯一路徑
⇒ **把收益低估一個數量級**：q=0.87 我推得 +0.8%，實為 **+17.2%**。
（錯誤方向是保守的：會害我們放棄值得做的東西。selftest 第 3 項釘死 `q=0 => f_clean == p_res0^U`。）

### ★ 真正的槓桿是「寬度」不是「準度」
門檻事件的指數是 **U=15.5**（整層 union），不是 8 ⇒ `0.87^15.5 = 11.6%` 比使用者算的
`0.87^8 = 33%` 嚴三倍。但因為 r 有 p_res0 當地板，門檻實際上**比使用者估的更低**。
`q_ceiling(k tokens)`：8 ids → 51.6%（+5.4%）／16 → 76.3%（+12.3%）／
**24 → 91.1%（+19.5%）**／32 → 100%（+25.8%）。損益兩平 step −10% 只要 **q ≥ 0.731**。

### ★★ 3 倍寬度是樹上現成的、被主動丟掉的
`llama-context.cpp:5390-5391` 的 draft 預測**只取 j=0 一行 8 個 ids**
（理由「verify 從第一個預測 token 驗證」——對 prefetch 優先順序成立，對 prebind 覆蓋率不成立）。
draft ctx 其實算好 **3 個 token × 8 = 24 個**。**改成取 j=0..n_tokens-1 是一行改動**，
q 上限 51.6% → 91.1%。這是整個 A 方案最便宜的一步。

### 相關性（使用者的直覺）量化了：幫忙，但買不到數量級
共用隨機效應 `r=logistic(mu+sigma*z)`：sigma 0→3 只把 f_clean 從 38.3% 拉到 74.8%（q=0.60）。
`r^U` 對 r 凸 ⇒ Jensen ⇒ 層內正相關確實有用。**先買寬度（不靠假設），相關性當安全邊際。**

### ★ M5 prerouter 已經實測過命中率：precision = 4.2%
`llama-expert-cache.cpp:1446-1521`（`CGC_PREROUTER`）＋ `docs/M3_M5_CLOSURE_2026-09-17.md`。
隨機基準 8/256 = 3.1% ⇒ **4.2% ≈ 隨機**。它用的是**全域頻率直方圖**
⇒ 結論：**路由邊際分佈幾乎是平的，沒有永遠熱的專家**。
- **不能**否定 A（A 靠時間局部性，與邊際平不平相容）；
- **能**否定 **C** 的機制：C 正是「按路由直方圖按層重分配」⇒ **沒得搬**。
- 但 C 仍是 **A 的乘數**：p_res0 0.85→0.95 讓寬度 8 的收益 +5.5%→+9.6%、門檻 q 0.731→0.578。

### ⚠ 一個必須先拆的矛盾：p_res0 有兩個差 3 倍的來源
註解 15% 冷 ⇒ 0.85；由 F1 模型 `cb = 0.46L + 0.695M` 反解實測 cb=39.3 ⇒ M≈30/step ⇒ **0.95**。
反驗：若 0.85，單 fill 項 `0.695×93 = 65 ms` 就超過實測 cb ⇒ **F1 係數與 ntok=4 實測不相容**。
⇒ 本工具**不用 F1 係數**，改校準線性代理。p_res0 是階段 0 要量的第三個數字。

### D（攤薄）的死因不是 fill，是分母
「k=3 比 k=2 慢」證據不乾淨（ntok=4 跨 `ggml-metal-ops.cpp:2590` 的 Q_K `ne11>=4` → 換 PSO）。
真正死因：**攤薄的分母是「接受數」不是 ntok**，`emit_tok_per_round = 2.000`。
但 **A 會把 D 翻正**：ntok 2→4 的 union 只漲 1.83×（次線性），只要 A 拿掉那 35 ms gap，
ntok=4 才第一次划算 ⇒ **D 是 A 的下游，不是獨立方向**。

### 階段 0 gate 改寫（原「`all_cov_layers/n_routable >= 0.5`」作廢）
改量 **q 本身**，門檻 **q(m=24) >= 0.73**；`all_clean/n_routable` 降為只記錄（它是 q 的函數）。
同時要印**真實 `uni_size`**（`CGC-HOOK` 截斷在 16，看不到真的 U）—— U 是指數的位置。

### B 的兩個前置條件（使用者沒寫出來）
① A 的 miss＝「掉回慢路徑、退化成今天」；B 的 miss＝「slot 沒資料、**靜默算錯**」
   ⇒ B 需要的是 miss 的**上界＝0**，不是平均值。
② A 的量測單位是「層」，B 需要「任何一層任何一刻」⇒ **A 的結果只夠決定 B 值不值得開規格。**

### 未解
`union_of_k_tokens` 的中間點是假設（s=0.6 幾何插值，只釘住 U(1)=8 與 U(4)=15.5）；
sigma 完全無實測；開 24 ids/層×40 層＝960 個/步的 LRU 擾動未模擬；截距 +8.0 ms 仍無解。

## §EN-463 「GPU/CPU 完全重疊有機會嗎」—— 定錨（2026-09-23，零 GPU，全讀既有文件）

承 §EN-462（prebind FAIL）。把「重疊」拆成**三個可各自為偽的命題**，逐個查既有判決：

### ① 算術上界（有，但不是方案）
步時 247.98 ms，CPU 獨佔 `cb` 的兩種口徑 ⇒ 完全重疊的收益：
- 同 run `cb=42.04` ⇒ −17.0% ⇒ 12.57 → **15.14 t/s**
- 分解式 `cb=74.18` ⇒ −29.9% ⇒ **17.94 t/s**
- L3 定錨 `gpu_sum=181.56` ⇒ −26.8% ⇒ **17.17 t/s**（文檔寫 18.59 是 @ml 3.375 的另一換算）
⇒ **量級 15–18 t/s（+20~48%）**。兩個儀器對 `cb` 差 1.8×（42 vs 74）本身是未閉合項。

### ② 結構窗口（= 0，§EN-408 已量測，0 重建）
segment 形狀 `[MoE core(L)] + [attn/GDN(L+1)] + [route(L+1)]`：
- MoE core 永遠在**第一個** command buffer（5811/6362，pre-MoE duration 佔比 med=0.000）；
- ids 由 segment 最後的 route 產出 ⇒ **CPU 拿到 ids 時 GPU 已空**；
- submit 後第一個 buffer 立刻是 MoE core(L+1) ⇒ issue 與 await 之間**沒有任何 GPU 工作**；
- 挪後不行：attn(L+2) 依賴 MoE core(L+1) 的輸出。
⇒ 交叉驗證 `gap 54.35 > cb 42.04` ⇒ GPU 空轉得比 fill 本身還久，遮蔽量零。

### ③ 三條「製造窗口」的路，全部堵死
| 路 | 狀態 | 堵死的原因（算術） |
|---|---|---|
| 預測 ids（prebind） | **今天證偽** | q24=0.354 vs 門檻 0.579（差 39%）；union 19.41 vs 每次能預測 8 ⇒ 天花板 41% |
| 背景鄰居預取（不需 ids） | **撤回** | 每專家分在 3 支獨立 GGUF 張量 ⇒ R=1 是 3 次 ×3 大的讀 ⇒ 步級 IO 309–429 ms vs GPU 陰影 159.77 ms，裝不進 |
| 全常駐（消滅 IO，重疊變無意義） | **記憶體堵死** | 專家全集 = 40 層 × 256 × 1.0703 MiB = **10.70 GiB**；工作集 11453 MB(11.18 GiB) − 非專家 4617 MiB(4.51 GiB) = 剩 6.68 GiB ⇒ **差 4.0 GiB** |

### ④ 部分重疊的樂觀上界（不是 0，但不划算）
「按 miss 數線性縮放」（`ensure_batch` 是批量，miss 數線性影響時間 ⇒ 這比 `f_clean` 口徑寬鬆）：
q=0.354 ⇒ miss 率 0.0953 → 0.0615 ⇒ 省 6.0%（cb=42）～10.6%（cb=74）⇒ 13.37～14.06 t/s。

⚠ 兩種口徑（`f_clean` 整層零 miss vs miss 數線性）對同一個 q 給不同結論，
但**都還沒算影子成本與 LRU 擾動**，算了都是淨虧 ⇒ 不影響判決。

### 結論
單流 decode 交付形狀下「完全重疊」**沒有機會**：上界是減法不是方案，窗口實測 0，三條路全堵。
剩下的是**降本**（`pread_usec`）不是重疊。唯一在結構上真能造窗口的是**多流互填**，
但那改變交付形狀，且 `-np` 已判「不是通往 25 的路」。

## §EN-464 「ids 誰算的？不能加速嗎」—— 定錨（2026-09-23，零 GPU，讀 `DECODE_CB_BREAKDOWN` + 源碼）

承 §EN-463。關鍵是**「加速 ids」與「提前 ids」是兩件完全不同的事**，天花板差 20 倍。

### ★ ids 誰算的
`ffn_moe_logits`（gate matmul）→ `ffn_moe_probs` → `ffn_moe_argsort/topk` **全在 GPU**；
CPU 只做 host read + unwrap，經 eval callback `llama_context::expert_cache_on_topk`
（`llama-context.cpp:5005`，dispatcher 定義 `cb = st2 - st1` 就是夾住它，`ggml-backend.cpp:2524`）。

### ★ 「加速 ids」= 沒戲（天花板 2.0% < 3% 門檻）
`CGC_HOOK_SPLIT` 唯一一份 log（`Backup/cgc_logs/llama_server_20260919_032308.log`，
權威 `docs/DECODE_CB_BREAKDOWN_2026-09-20.md`）把 hook 切四塊：
    pre（診斷 + top-k unwrap + union 建構） **4.1 µs/call  → 佔 cb 0.55%**
    **ensure（批次 pread）                 736.4 µs/call → 佔 cb 99.4%**
    drain 0.3 / tail 0.4 µs/call
⇒ CPU 側「處理 ids」只佔 cb 的 **0.55%**；再加 GPU 側算 route 的
（logits+probs+argsort = 69.2+49.8 µs/segment × 40 = 4.76 ms/步 = 步時 1.9%）
⇒ **「把 ids 算快、讀快」的總天花板 ≈ 2.0%，低於 3% 門檻。靶子是 IO 不是 ids。**

### ★ 但「提前 ids」有戲 —— 而且這是唯一還沒被證偽的造窗口方向
思路：route(L) 的輸入是 `norm(h after attn(L))`。在 **MoE core(L-1) 一結束**就用 `h` 去算
gate(L)（跳過 attn(L) 的增量）⇒ 得到**近似** ids(L) ⇒ 立刻發起 fill(L)。
與 prebind 的本質差別：prebind 是**跨 token**（時間局部性，實測 q24=0.354）；
這是**同 token、只差一個 submodule**（殘差流局部性），而且是真實 matmul 不是猜
⇒ **不必加寬**（保持 top-8）⇒ **沒有 prebind 那個 38.3 ms 的影子成本**。

**窗口算術（這是關鍵，而且窗口裝不滿）**：
- MoE core 佔 segment **60.1%**（NSM dump：首 buffer 1959.2 µs，下一個 cum=60.1%）
  ⇒ 提前發起最早只能在 segment 的 60% 處 ⇒ **窗口 = segment 的後 40%**
- segment = 4.00 ms（GPU span 159.81/40）或 3.26 ms（NSM dump）⇒ 窗口 = **1.59 / 1.30 ms**
- 每層 fill = 74.18/40 = **1.855 ms** ⇒ **裝不進**（差 16% / 43%）
  ⇒ 最多移出 **70~86%**，溢出 0.26~0.56 ms/層仍在臨界路徑
- 成本：插入的 gate+topk = 4.76 ms/步（GPU 單佇列串行，直接加在步時上）

### 既有結論（不要重做）

### ★ 三個結論，都有數字
1. **機制是對的**：hit% 61.4 → 87.4（+26 pp），讀的位元組 8.80 → 3.18 GiB（**−64%**）。

## §EN-471 expert cache → Metal 的「shape」第一性原理審計（22:1x，零量測）

**使用者澄清**：問的不是張量 ne/nb 自洽，而是**時間形狀**——CPU(IO)/GPU 重疊、頻寬打滿、並行。
方法：只從 GGUF 幾何＋設備常數推，**沒跑 benchmark**（符合 METHODOLOGY_RETROSPECTIVE §3 三步法第一步）。

### 唯一的那個數：1 expert slot = **1.0703 MiB**（全流程從它長出來）

從 models/gguf/Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf 直讀
（`blk.0.ffn_*_exps.weight` ne=[2048,512,256] / [512,2048,256]，每專家 1,048,576 elem = 4096 block）：
- gate/up IQ2_S 2.5625bpw × 82 B/block = **335,872 B**
- down  IQ3_S 3.4375bpw × 110 B/block = **450,560 B**
- 合計 **1,122,304 B = 1.0703 MiB**

**三源閉合（重要）**：實測 8.80 GiB / 8446 miss = **1.0669 MiB** ⇒ 差 **0.3%**；且與 log 的
`requested=335872/450560` 同組數字。⇒ 這是「不可壓縮成本」，不是策略。

### ★ 最硬的一條判決：prebind／ρ 的提前一步預測被物理否掉

```
一步所需 union = 40 層 × U=19.36 = 774 slots = 829 MiB
設備搬完 829 MiB = 829/1638 MiB/s = 506 ms = 2.04 × step(247.98 ms)
```
⇒ **一個 step 絕對搬不完它自己需要的全部專家。完美預測也救不了**（需求 829 vs 供 406 MiB＝2.04×）。
⇒ prebind 天花板不是「預測準不準」，是這個比值。先前「prebind 上界 14.33~16.06」是同一件事的另一種看法，
　但這次是從檔案幾何推出，**不依賴覆蓋率／接受率模型**。

### 三軸判決

| 軸 | 現狀 | 判決 |
|---|---|---|
| 頻寬打滿 | duty cycle 32~79% | **偽目標**。設備一步供 406 MiB；「打滿」＝硬搬無用位元組 |
| CPU/GPU 重疊 | 41 段 ping-pong，GPU gap 44.4 ms/step | **真目標但未達成**，且**餘量只剩 21%**（悲觀情形 IO 已吃 79% step） |
| 並行 | 每次 0.229 MiB（base）／0.041 MiB（ρ） | **粒度錯**。理論粒度＝1.0703 MiB ⇒ 碎片 4.7×／26× |

悲觀/樂觀兩種口徑（miss 率 38.6%）：
- 樂觀（draft-like，每層 top8 去重）：req/step 311 → miss 120 → 128 MiB → **78 ms（32% step）**
- 悲觀（verify ntok=4 union）：req/step 774 → miss 299 → 320 MiB → **195 ms（79% step）**

### ★★ 命中率不是預測決定的，是「記憶體能放幾個專家」決定的

```
8 GiB budget / 1.0703 MiB = 7654 slots = 191/layer ⇒ 覆蓋率 74.7%
resident 6430.62 MiB      = 6008 slots = 150/layer ⇒ 覆蓋率 58.7%
實測 hit rate = 61.4%      ⇒ 差 2.7pp
```
⇒ **hit% ≈ 覆蓋率**。槓桿在 `per-expert bytes↓`／`budget↑`，**不在預測器**。

### 順手查清：gather slab 的跨層 max stride —— **不是 decode 收益，別修**

`llama-context.cpp:721` 註釋：mixed quant，41 層有 8 種 (kind,stride)
（kind0/1 = 335,872/450,560/344,064；kind2 = 450,560/557,056）。
`CGC-GATHER-SLAB` 的 per-slot stride 取**全模型最大值** ⇒ iq2_s 層 padding 34.1%、down 23.6%。
但：① `fill_pool_direct_collect` 的 `seg.bytes = e.bytes`（真實大小）⇒ **pread 沒多讀，頻寬沒浪費**；
② decode 的 8 GiB expert pool 是 **per-layer stride**（`llama.cpp:522` `total += r.slots*r.stride`）⇒ 不受影響。

### 結論：最佳 shape 重新定義

**「少而大、按層塊提前、粒度＝一個專家」** ≠ 「多而早、逐 segment、指望預測」。
這也解釋了 ρ 為什麼失敗：它把請求數 ×2.04、粒度 ÷5.6，而通道只剩 21% 餘量。

**待閉合**：req/step 兩口徑（311 vs 774）需 CGC-DECPROF 分層；miss 率全域均勻是假設；pool 的 `r.stride` 未逐層核對。

**產物**：`docs/EXPERT_IO_SHAPE_FIRST_PRINCIPLES_2026-09-23.md`；探針 `/tmp/expert_shape_probe.py`。

## §EN-472 「現在的 shape 能到 decode 25 t/s 嗎」→ 判決：**不能**（22:5x，0 benchmark）

**產物**：`docs/DECODE_25TPS_VERDICT_2026-09-23.md`（純結帳，無重建、無起 server）。

### 先把標的換單位（否則所有數字不能比）

交付 cell 12.57 t/s × step 247.98 ms ⇒ **每 step 產 3.117 token**（接受率 77.9%，k=3 上限 4）。
⇒ **25 t/s（接受率不變）要求 step ≤ 3.117/25 = 124.7 ms**。這 124.7 是全判決的尺。

### ★ 核心：GPU busy 單獨就超過整份預算

| GPU busy 來源 | ms/step | vs 124.7 |
|---|---:|---:|
| 細切（`DEVICE_BUSY_ATTRIBUTED` §1.2, T=4 n=48, `CGC_CB_N_MAIN=1`）wait | **142.6** | 超 14.4% |
| 舊 `gpu_sum`（`CEILING_STACK` L3 基石） | **181.6** | 超 45.6% |

⇒ **IO 完全免費、一毫秒不花，今天的 GPU 也算不到 25 t/s。**
⇒ 這不是「重疊不夠」——重疊做到滿只是把 cb 拿掉，GPU busy 一分不少。

### shape 的上限 = **20.49 t/s**（不是 25）

細切 decompose：wait 142.6 + cb 81.1 + submit 9.5 ≈ 234.6 ms。
- cb **完全藏起來**（shape 天花板）⇒ 152.1 ms ⇒ **20.49 t/s**（-22% vs 25）
- 同口徑用舊 gpu_sum ⇒ 191.1 ms ⇒ **16.31 t/s**

反解：25 t/s 需 GPU busy ≤ 124.7−9.5 = **115.2 ms**
⇒ GPU 本身要比細切實測**快 19.2%**、比舊 gpu_sum **快 36.6%**。**這是 kernel 的事，不是 shape 的事。**

### 四條獨立線索全部落在 16~21.7，沒有一條碰到 25

| 日期 | 產物 | 極限 | 方法 |
|---|---|---:|---|
| 09-19 | `DECODE_25TPS_TWO_ALGORITHMS` | **21.7** | GPU busy 46 ms/token 硬牆 |
| 09-21 | `CEILING_STACK` L3（重疊做滿） | **18.59** | gpu_sum 181.56 |
| 09-23 | `DEVICE_BUSY_ATTRIBUTED` 細切 | **20.49** | wait 142.6 + submit 9.5 |
| 09-23 | 本篇（§EN-471 延伸） | **20.49** | IO 通道餘量僅 21% |

> 09-19 那份標題就是「推向 20–25」，但它自己在同一份寫下否決自己的算式（21.7）。
> 兩天後三條獨立路徑收斂到同區間 ⇒ **沒有新事證就不要再結這個案**。

### ★ 「乾脆全常駐、不要 cache」被**內存**堵死（不是被頻寬）

```
模型檔 12.72 GiB = 專家 10.70（40×256×1.0703 MiB） + dense 2.02
機器 hw.memsize = 16.00 GiB（Apple M4，**統一內存**，不是獨立顯卡）
⇒ 全常駐佔 79.5%，只剩 3.28 GiB 給 macOS + GPU working set + KV cache(ctx 4096)
⇒ 必然進 swap。而 swap 已知致命：5301 MiB 時 hit% 68.7→57.2、base 12.57 → **4.62**。
```
⇒ **expert cache 不是優化選項，是被 16 GiB 強制的物理約束。**

### 唯一理論通路（幻影）與它的否決

要 25 t/s 須**同時**滿足兩個不可達條件：接受率打到 k=3 滿值 **4.0**（現 3.117）＋ cb 100% 隱藏
且 GPU busy 取樂觀口徑 ⇒ 26.30 t/s（邊際僅 +5.2%）。任一不成立 ⇒ 跌回 16.3~20.5。

而唯一能真壓 GPU busy 的主線 **K5／L2** 早已在 09-21 結案：**判 (C) 成立 ⇒ 30–38% 上界作廢
⇒ L2 歸零 ⇒ M-K5 不做**（§EN-406／§EN-414）。若它還活著，帳會是 28.5~31.8 t/s —— 但已被證偽。

### 判決

**不能，差 22%，缺口在 GPU 算力不在 IO/shape。維持 MEMORY.md 既有 `P(25) < 3%`。**
誠實的 target 不是 25，而是 **cb 隱藏率**：今天 0%；60% ⇒ 17.65；85% ⇒ 19.04；100%（不可達）⇒ 20.49。
再往上要動的是 kernel。

## §EN-474 「expert cache 改用 FlashMLX 如何」→ 判決：**不換**（23:4x，0 量測）

**產物**：`docs/FLASHMLX_EVALUATION_2026-09-23.md`。

### 先分清兩個同名專案（搜尋會撞）

- **anemll-flash-mlx**（Flash-MoE, MLX, slot-bank + ids-as-data, SSD 串流）← 本次標的
- **szibis/mlx-flash**（Python+Rust, 15 技術, 招牌＝entropy coding「65% smaller」）

### ★ 架構前提：不能「只換 expert cache」

對方 README：「dense path 留在後端，sparse path 用 stable slot-bank + ids」。**它假設整個模型都在 MLX**。
我們這邊 pool 就是 **Metal buffer**（`L4 metal pool: 143 slots/layer`，slot 直接餵 `mul_mat_id` src0）
⇒ 換過去＝兩套 runtime／兩條 command queue／兩份記憶體池。加上 **IQ2_S/IQ3_S 是 llama.cpp i-quant，MLX 沒有**
⇒ 要重新匯出 sidecar；且它 targets **Qwen3.5**（我們是 3.6）⇒ **連模型一起換**。
⇒ 「換 expert cache」實為「換掉整個推論 runtime」。

### 三條硬帳

**① 量化倒退**（per-expert，我們從 GGUF 直讀 = 1.0703 MiB）

| 來源 | per-expert | vs 我們 | resident 6153.7 MiB 下的覆蓋率 |
|---|---:|---:|---:|
| 我們 IQ2_S×2+IQ3_S | **1.0703 MiB** | — | **56.1%**（143.7/層） |
| MLX 4-bit | 1.6117 MiB | **+51%** | **37.3%** ← 崩 |
| MLX UD-Q2_K_XL | 0.8965 MiB | −16% | 67.0% |

⇒ 4-bit 災難；UD-Q2 只是「更低 bpw」，**在 llama.cpp 裡直接做即可**（＝§EN-473 的 per-expert bytes↓ 變體）。

**② entropy coding 在本機是負收益**（mlx-flash 招牌技術）

```
讀 1.0703 MiB @ 1638 MiB/s = 0.653 ms；壓到 65% 紅利 = 0.229 ms/專家
⇒ 解壓須 < 0.229 ms ⇒ 需 4.6 GiB/s CPU 解壓頻寬
單核 Huffman 7.48ms / 8 緒 1.87ms / 樂觀 1.2GB/s 0.94ms ⇒ 三種全虧
```
⇒ SSD 1.6 GiB/s 比 CPU 解壓快一個數量級 ⇒ 拿 CPU 換 IO 是反的。
（Apple *LLM in a Flash* 與 mlx-flash 的前提「IO 遠慢於 CPU」在 M4 + 高速 NVMe 上不成立。）

**③ miss 代價斜率：我們比較有效率**

| | miss | 損失 | 斜率 |
|---|---:|---:|---:|
| FlashMLX（94.5→47.1 @82.7%） | 17.3% | 50.2% | **2.90%/pp** |
| 我們（15.14→12.57 @61.4%） | 38.6% | 17.0% | **0.44%/pp** |

⇒ 6.6×。我們 miss 走 bg thread + 41 段填充有部分隱藏（cb 只佔 step 17%）；對方像是同步阻塞。
⇒ **換過去 IO 隱藏不會更好，很可能更差。**

### 其他

- 對方 benchmark 全在 **M5 Max 128 GB**（resident 94.5/101.6、slot-bank128 47.1@82.7%、16 槽 17.1@59.5%）。
  本機 **M4 / 8 核 GPU / 16 GB 統一內存 / MacBook Air 無風扇** ⇒ t/s 絕對值**完全不可比**。
  網傳「MLX 130 vs llama.cpp 43」是 M4 Pro 64GB **全常駐**，本機裝不下 ⇒ 那 3× 不適用。
- 換過去會**失去 MTP**（每 step 3.117 token；MTP off 9.82 vs on 12.62 = **+28.5%**）⇒ 直接歸零。
- 本機 `import mlx` **失敗**（未安裝）。

### ★ 唯一值得抄的：oracle all-hit replay

`REMAINING_LEVERS` §1 那張表（+1.5GiB⇒13.39／+3GiB⇒14.33／全常駐⇒15.14）是**外推**（假設 hit≈覆蓋+5.5pp）。
對方 `bench_slot_bank_oracle_hits.py` 的做法：錄 ids 序列，miss 時**不讀盤直接複用 slot**
⇒ 得到「數學錯誤、時間正確」的上界。**不需擠出記憶體**（繞過 §EN-473 第 0 步這個未解前提）、不需重建格式。

### 判決

**不換。** 換的不是模組是 runtime；唯一不倒退的選項（per-expert ↓16%）在 llama.cpp 直接做即可。
真正該做的仍是 `REMAINING_LEVERS` 的順序（第 0 步＝印 KV cache 佔用，決定池能加多大）。

**待閉合**：對方 k=4 vs 我們 top-8（若屬實，對方每 token 讀專家量只有我們一半 ⇒ ③ 的差距被放大）；
`--slot-bank 128` 47.1 是否含 Python 開銷。

## §EN-475 oracle all-hit replay「能提升啥」→ **0 t/s，提升的是決策**（23:5x，0 量測）

**產物**：`docs/ORACLE_HIT_REPLAY_DESIGN_2026-09-23.md`。（承接 §EN-474 從 FlashMLX 抄來的

它把「要不要投數小時做池加大」變成 30 分鐘的判定。

### ★★ 最有力的發現：換替換策略 ≈ 加 1.5 GiB，而且**免費**

| hit% | miss% | cb→ms | step | t/s |
|---:|---:|---:|---:|---:|
| 61.4（今天） | 38.6 | 42.0 | 248.0 | **12.57** |
| 75.0 | 25.0 | 27.2 | 233.2 | **13.37** |
| 100 | 0 | 0 | 205.9 | **15.14** |

- 換替換策略到 hit 75% ⇒ **13.37 t/s（+6.4%），0 記憶體**
- §EN-473 表的「池 +1.5 GiB」⇒ 13.39 t/s ⇒ **兩者差 0.04 t/s，幾乎完全等價**
⇒ **換策略是繞過 §EN-473 第 0 步（記憶體從哪來，KV cache 未印）的一條路**。

### 三項產出

1. **「cb 全藏」從外推變實測**：oracle（miss 時跳過 pread，內容垃圾但時間正確）
   ⇒ 反推真實可藏 cb：X=13.0 ⇒ 只藏 8.2 ms；X=15.14 ⇒ 藏 42.1 ms。
2. **命中率曲線**：錄 ids 後純 CPU 重放任意 slots/layer ⇒ 不需真分配記憶體。

3. **替換策略上界**：同份 trace 比 LRU / **SpAc EMA（生產用）** / **Belady（最優）** ⇒ 全免費。
   Belady − SpAc = 「換策略」這條路的剩餘空間。

### 決策分支（oracle 實測 X）

| X | 判決 |
|---:|---|
| < 13.5 | 池加大**整條路作廢** ⇒ 轉 attention/GDN kernel 地板（§EN-473 第二名） |
| 13.5~14.5 | 邊際 ⇒ 只做便宜變體（per-expert bytes↓） |
| > 14.5 | 值得做 ⇒ 才去執行第 0 步 |

### 設計與陷阱

- `CGC_EXPERT_TRACE=<path>`：錄製點 `llama_expert_cache_ensure_batch()`（`llama-expert-cache.cpp:1002`），
  **host 側 ids 本來就有**。量：40 層 × 19.4 × 164 步 ≈ 127k ids ≈ 0.5 MB。
- `CGC_ORACLE_HIT=1`：miss 時**只跳過 pread**，其餘（`slot_loading/queued`、pin 邏輯、`spac_update` EMA、
  LRU tick）全部保持 ⇒ 只改「有沒有讀 bytes」，不改控制流。
- ⚠ 陷阱 1：oracle 內容是垃圾 ⇒ 後續路由會變 ⇒ **trace 與 oracle 必須分兩次跑**（trace 用正常模式）。
- ⚠ 陷阱 2：**生產是 `CGC_SPAC=1` 的 SpAc EMA-utility victim，不是純 LRU**（`llama-expert-cache.cpp:593`；
  且 09-15 修過 `best_util` 初值 2.0 → +inf 的 crash）⇒ 重放要複刻 EMA，複刻不了就用 LRU/Belady 包區間。
- ⚠ 陷阱 3：`cb ∝ miss` 是一階近似；oracle 實測 X 本身就是它的檢驗（X=13 ⇒ 假設破）。

### 歸屬（重要）

oracle 要改 `llama-expert-cache.cpp` 的**命中／替換／IO 路徑** ⇒ 按 09-20 分工屬**線 I**（`cb`／快取命中儀器）。
**本線（WorkBuddy/freebuff）＝靜態分析／長報告 ⇒ 只出設計，不實作。**
本線可協助寫 `scripts/check/oracle_hit_replay.py`（`scripts/check/` 屬本線）。
