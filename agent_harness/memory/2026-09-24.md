## §EN-477「我們的能力高於 FlashMLX 嗎」→ 分維度判決（00:2x，0 benchmark）

**產物**：`docs/CAPABILITY_VS_FLASHMLX_2026-09-24.md`。純靜態對比既有實測數字，沒跑任何 benchmark。
承接 §EN-474（換框架評估）＋ §EN-476（靜態 pin 實測 89.4%）。

### ★ 先拆「能力」——不拆就沒有答案

絕對 t/s 差 3.7~7.5×，但**那不是演算法**：對方 M5 Max 128 GB，本機 M4 / 8 核 GPU / 16 GB 無風扇。
⇒ 必須挑**無量綱**或**已歸一化**的指標，否則「誰強」是偽問題。

### ★ ① miss 代價斜率 —— 唯一乾淨的可比指標

定義：每 1pp 的 miss 吃掉多少 % 吞吐（越低 = SSD path 越有效率）。

```
FlashMLX : 94.5(100% hit) -> 47.1(82.7%)   損失 50.2% / 17.3pp = 2.90 %/pp
我們     : 15.14(100% hit) -> 12.57(61.4%) 損失 17.0% / 38.6pp = 0.44 %/pp
```

⇒ **我們對 miss 的魯棒性是對方的 6.6 倍**。對方 miss 17.3pp 掉一半吞吐；我們 miss 38.6pp 只掉 17%。
成因：我們 miss 走 bg thread + 41 段填充，IO 部分藏進 GPU 空檔（`cb` 只佔 step 17%）；
對方 slot-bank miss path 表現得像**同步阻塞**。
⚠ 我方 15.14 是外推（cb 全藏），非實測；用 `DEVICE_BUSY` 交叉驗證的 15.8 重算 = 0.48 %/pp，結論不變
⇒ **這個對比對我方偏保守**（對方 94.5 是實測）。

### ★ ② 命中率錯配：我們剩 9.5pp，對方剩 16.2pp

借用我方實測的重尾上界（K=128→98.2%、K=143→98.9%）**作為對方上界是假設**（架構同源，量級可信）：

| | 覆蓋率 | 實測 hit | 錯配 |
|---|---:|---:|---:|
| **我們 PIN_PROFILE** | 55.9%（143 槽） | **89.4%** | **9.5 pp** |
| FlashMLX slot-bank 128 | 50.0% | 82.7% | 16.2 pp |
| FlashMLX slot-bank 64 | 25.0% | 80.8% | 18.1 pp |
| FlashMLX slot-bank 16 | 6.3% | 59.5% | 39.4 pp |

⇒ 命中率我方高 **6.7pp**，按覆蓋率歸一化後錯配仍高 6.7pp。
⇒ **「重尾 + 靜態釘住」這個洞察對方沒用上**（他們用動態 slot-bank）。

**反直覺但自洽的推論**：同一個洞察在誰身上更值錢？
- 給對方（82.7→89.4，+6.7pp）× 2.90 %/pp ⇒ **+19%**（47.1 → 56.3）

⇒ 對 miss 越敏感的系統，提命中率越值錢；我們「只」值 12% 是因為**我們本來就不太怕 miss**。

### ③ 每專家位元組：我們比其主力格式省 34%

## §EN-478 解釋「裝置 span 56-61%」與「回合固定成本攤薄」（00:4x，0 量測）

純釋義＋溯源，沒跑任何 benchmark。全部數字來自既有 docs。

### ⚠ 先糾一個口徑：「56-61%」其實是**三個不同的數**，別混用

| 數字 | 出處 | 真實含義 | 口徑 |
|---|---|---|---|
| **56%** | `M3_M4_STATUS_2026-09-17.md:55` | GPU span 82.84 / step 148.43 | **MTP off** 那個 cell（6.7 t/s），**不是 verify cell** |
| **61.3%** | `K5_VERDICT_2026-09-21.md:13,118` | GPU 時間裡 61.3% 落在每步 ~44 個「64 節點 command buffer」 | **歸屬**，不是佔 step 的比例 |
| **71.3%** | `STEP_SERIALIZATION_2026-09-23.md` §1 | union 113.4 / total 161.0 | **★ 最新穩態 verify 賬（n=221），這才是該引用的** |

⇒ 用戶說的「56-61%」最接近 **union 佔 step 的比例**，但權威值應取 **71.3%**（gap 只剩 27.9%）。
⇒ 61.3% 那條是另一件事（`n_main = MAX(64, 0.1×n_nodes)` 那段強制打包的主 buffer，2334.1 µs、
   44.5 個/步對上 `segs=40`），它回答「GPU 忙的時間是誰佔的」，不是「GPU 有多忙」。

### ① 裝置 span（`union`）是什麼

定義：把該 step 所有 command buffer 的 Metal `GPUStartTime/GPUEndTime` 疊到**同一條時間軸**上，
取 `max(end) − min(start)` ⇒ 設備真正被佔用的跨度。

**與 `gpu_sum` 的差別（關鍵）**：`gpu_sum = Σ(end−start)`，**重疊的 buffer 會被重複計算**
⇒ 可以 >100%（實測 168.3 ms = 105.8%）。所以 `gpu_sum` 是「假的钱」，結帳要用 `union`。
（這也是 `DEVICE_BUSY_ATTRIBUTED` 警告 `gpu_sum` 不可引用的原因之一。）

**最新穩態賬**（中位數，n=221，`segs=41` 排除 draft 廉價 step）：

| 量 | ms | 佔 total | 是什麼 |
|---|---:|---:|---|
| total | 161.0 | 100% | CPU 側串接 = wait+cb+submit |
| wait | 123.2 | 78.1% | CPU 自旋等 GPU 跑完這一段 |
| cb | 23.8 | 15.0% | top-k hook：slot 分配＋阻塞式填池 |
| submit | 10.8 | 7.0% | 提交下一段的 CPU 時間 |
| **union** | **113.4** | **71.3%** | **GPU 真正忙的跨度** |
| **gap** | **44.4** | **27.9%** | **GPU 空窗** |

閉合 `union+gap = 157.8` vs `total 161.0`（差 3.2 ms, 2%）⇒ 兩個時鐘對得上，可互相引用。

**為什麼是「大頭」**：gap 44.4 ms 是 union 之外最大的一塊；全消 ⇒ step 161 → 113.4（**1.42×**）。
（09-17 MTP-off cell 的同樣算法：148.43 → 82.84 = **1.79×**，因為那時 gap 佔 46%。）

**但 gap ≠ 可回收**：回歸 `gap` vs `cb+submit` ⇒ **r=0.957、slope=1.05、截距 +10.1 ms**
⇒ 幾乎 1:1：**GPU 空轉 = CPU 在 hook 與 submit 上花的時間**，不是「GPU 沒事幹在等資料」。
而且 `L3_WINDOW_ZERO` 實測 MoE 永遠在 segment 第一個 buffer（5811/5811）⇒ **可遮窗口 = 0**
⇒ 用「提前 fill」藏不掉。⇒ 要拿掉的是 **CPU 在關鍵路徑上的位置**（方案 A 預指派 slot）。
另：`cb` 裡固定項（每層 barrier ≈ 12.9 ms/step）比真正搬資料（≈11 ms）還大。

### ② 回合固定成本攤薄是什麼

**最硬的證據**（`DECODE_25TPS_TWO_ALGORITHMS_2026-09-19.md:100-112`）：

| | 每 token 的 expert union | 每 token 牆鐘 |
|---|---:|---:|
| trunk verify（T≈2.4–3.5） | 7.8 | **10.1 ms** |
| **draft forward（T=1）** | **8.00** | **~40 ms** |

**一樣的 expert 數，貴 4 倍。** ⇒ 40 ms 裡絕大多數是**每次呼叫的固定成本**
（圖建構 + 提交 + sync + 取樣），而 draft 是 K 個**獨立的 1-token 呼叫**
（`llama_decode(ctx_dft, batch)`，`common/speculative.cpp` 多處）。
⇒ verify 那條 T≈2.4-3.5 把同樣的 MoE 做到 10.1 ms/token ⇒ **批次化把固定成本攤掉了**。

**機制層**（`DECODE_STEP_WHY_SLOW_2026-09-21.md:72-80`）：
- 大塊搬運其實不差：expert gather 吃到峰值 **50-61%**
- 但一個 **RMS_NORM 節點燒掉 57-92 µs 只搬 64 KB** ＝ 峰值的 **0.6%**，比 matmul 差近 100 倍
- ⇒ **2455 個工作節點，每一個都付了一次幾十 µs 的固定成本**
- **DRAM 只用了 11%** ⇒ 既非 FLOPs 牆也非 DRAM 牆，是第三類：**latency / occupancy-bound**
- `K0_RESULT`：一個 command buffer 的固定成本 ≈ **13 µs**（1-node buffer 中位數）

**方案 D 的數字**（`STEP_SERIALIZATION` §4）：`emit_tok_per_round = 2.000` ⇒ 約
**24 ms/step 的固定成本只攤在 2 個 token 上**。提高 token/step 可攤薄，
**但不免費**：ntok 變大 ⇒ 每層 union 變大 ⇒ fill 變多。
（`emit_tok_per_round` 各 cell 不同：2.000（k sweep）～3.314（bench 第 3 輪累計），
交付 cell 由 12.57×247.98 反推 = **3.117**。）

**⚠ 重要修正**（`ROUND_REMAINDER` §2）：verify 確實是**逐 token** 的
（`CGC-DECPROF` ntok 分佈：k1 只有 1/2/8，k3 才有 4）⇒「第 2 個 verify token 要付第 1 個的
98% 成本」是對的，因為它真的重跑一次完整的 41 段 step。
且 **steps/round = 1.55~2.30**（k1 ~1.5、k3 ~2.3）⇒ round ≠ step，`round_ms` 不能被單 step 解釋。

### 兩者的關係（我的判讀）

- **裝置 span / gap**：**時間軸上的洞**。設備只忙 71.3%，27.9% 在等 CPU。**這是最大的一塊**，
  但處方是「把 CPU 從關鍵路徑拿掉」（M-S2／方案 A），不是加速任何計算。
- **固定成本攤薄**：**每次呼叫的入場費**。24 ms/step 只攤 2~3.1 個 token；
  攤到 4 個（k=3 滿）省 ~2 ms/token ⇒ **量級比 gap 小**，且受「ntok↑ ⇒ union↑ ⇒ fill↑」抵消。

⇒ 兩者都指向同一個結論：**瓶頸不是算力也不是頻寬，是「每次呼叫的固定成本 × 呼叫次數」**。
區別只在於一個發生在段之間（gap），一個發生在呼叫之內（per-node launch）。

## §EN-479「怎麼消除 gap 44.4 ms」→ 方案 A，且 PIN_PROFILE 是它的基礎設施（01:0x，0 量測）

**產物**：`docs/GAP_ELIMINATION_PLAN_2026-09-24.md`。純結帳＋溯源，沒跑 benchmark。

### ★ 最重要的一句：gap 不是「GPU 在等資料」，是「GPU 在等 CPU」

三條獨立事證：① `gap` vs `cb+submit` 回歸 **r=0.957, slope=1.05, 截距 +10.1 ms**；
② `L3_WINDOW_ZERO`：MoE 永遠在 segment 第一個 buffer（5811/5811）⇒ 可遮窗口 = 0；
③ ρ 實測 hit +26pp、讀位元組 −64%，但 **t/s −21%**（`fill_wait_us` 44 ms→15.4 s）。
⇒ **空轉本身就是 CPU 造成的，而 CPU 卡在那裡正是為了做 hook ⇒ 循環，不是洞。**
⇒ 任何「把 IO 藏進 GPU 空檔」註定失敗（ρ／prebind／M-PF／段拆分／背景預取全是這一類）。

### gap 的成分（回歸拆，預測 46.4 vs 實測 44.4，差 2.0）

| 成分 | ms | 佔 |
|---|---:|---:|
| ① cb：CPU 在 top-k hook 阻塞填池 | 25.0 | 56% |
| ② submit：CPU 提交下一段 | 11.3 | 26% |
| ③ 啟動偏斜截距 | 10.1 | 23% |

⚠ `cb` 23.8 內部：固定項每層 barrier ≈ **12.9 ms/step** > 真搬資料 11.0 ⇒ **超過一半的 cb 不是 IO**。
⚠ 截距 10.1/41 段 = 0.246 ms/段，而 K0 實測單 buffer 固定成本僅 **13 µs**（差 19 倍）
⇒ 不是 per-buffer 啟動，更像段間同步/排空 ⇒ 「減少段數」可能是獨立槓桿（未驗）。

## §EN-11xx（23:2x）swap 對 3a/3b/3c 的分項影響 ＋ 3a 落地

### A. ★ swap 要分「水位」與「速率」，只有後者有害

`sysctl vm.swapusage` 給的是**水位**；壓力要看 **`vm_stat` 的單位時間增量**。
實測 23:2x：`used = 4.69 GB`（跑的時候一度 6.47 GB），但 **pageouts/5s = 0、pageins/5s = 0**
⇒ 換出去的都是冷頁，無害。累計 `Swapouts 10.03M / Swapins 5.80M` pages 是**歷史總量**，
**不要拿它當壓力指標**。

### B. 但 swap 是結構性的：`llama-expert-cache.cpp:491` 自己寫了原因

> "12.7 GB model (**--no-mmap**) + 8 GiB pool over-commits RAM, swap"

⇒ 模型 `--no-mmap` ⇒ 12.7 GB **常駐不可換出**；＋池 8 GiB = ~20.7 GB > 16 GB 實體
⇒ **池頁必然有一部分在 swap**，每次跑都會發生，不是「今天機器忙」。
而 `CGC_POOL_MADVISE`（P1/P2，丟頁）今天所有臂都是 **0（關）**。

### C. 分項判定

- **3a（vmask 乘 gate）不受影響**：純 GPU 圖，每層 +2 節點（CAST+MUL），不新增記憶體、不碰池；
  判據是**正確性**不是速度 ⇒ 短跑即可。
- **3b（fill＋計時器）決定性影響**：fill = `pread` 到**池地址**，池頁在 swap ⇒ 寫入前 swap-in
  ⇒ 這段延遲混進「fill 的固定開銷」。

### D. ★★ 連帶：§EN-10xx 的發現 B 要打折（我自己推翻自己）

優化方向完全不同（變成「固定池／縮小常駐」而不是「batch 化 pread」）。
⇒ **§EN-10xx 發現 B 狀態改為「未定案」。**
⇒ 3b 的計時器實驗**必須帶一組 `CGC_POOL_MADVISE=1`（或 2）對照**，否則 `fill_ms/step` 不可解釋。
⇒ 附帶：**swap 水位漂移 ⇒ 跨時間 A/B 配對不可靠**；每次配對要記 `sysctl vm.swapusage`
