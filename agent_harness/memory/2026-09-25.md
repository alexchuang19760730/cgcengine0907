`fill_segments_pool`（`llama-expert-cache.cpp:3618-3676`）：把一批 segment 按
`(file_idx, file_offset)` **排序**，再把 **file-contiguous 的 run 合成一次 `preadv`**
（`iovec`，`job.bytes = total`，一次 syscall 寫多個分散 dst）。
實測輸出直接寫著 **`(0.03 MiB/job as one contiguous run)`**。
⇒ 「一次 pread 搬多個 expert」**已實現**（文件建議的方向沒錯，但活已經幹過了）。

### (b) ★ 指標要用對（`io_us_per_job` 是累加口徑，會誤導 30×）
skill 規定：**IO 單價一律用 `fill_batch_usec / file_reads`**。

| run | fill_batch/job | KiB/job | jobs | misses | jobs/miss |
|---|---|---|---|---|---|
| mw_ctrl（生產 W8） | **371 µs** | 28 | 81798 | 4668 | 17.52（含 prefill slab 讀） |
| mw_w2（生產 W2） | 335 µs | 31 | 82512 | 4907 | 16.82 |
| r5_fill（自拼） | **151 µs** | 252 | 43128 | 9769 | **4.41**（純 demand） |
| a4_ctrl（自拼） | 113 µs | 236 | 38124 | 8092 | 4.71 |

⚠ 生產口徑的 `28 KiB/job` **不代表 demand fill 的大小**——它的分子含 prefill 的 slab 流式讀
（`slab fills disk=24.5 GiB`，見 §EN-1333）。**純 demand 的大小要看自拼 cell：236~252 KiB/job。**

### (c) ★★ 固定開銷佔 **90%**（這條把文件的建議量化了）
生產口徑：一個 job 共 **371 µs**，其中傳輸 28 KiB @760 MiB/s = **36 µs**
⇒ **固定開銷 ≈ 335 µs（90%）**，傳輸只佔 **10%**。
（物理基線 `pread_cost_probe`：冷讀 0.37 MiB 一次 = 487 µs / 760 MiB/s。）
⇒ 文件說的「瓶頸是每次 fill 的固定開銷（pread syscall ＋ bg_cv 喚醒 ＋ 一次同步點），
不是 bytes」**完全正確，而且比預期更極端**。

### (d) ⛔ 但可合併的機會已被幾何鎖死 ⇒ 收益 ~2.9%
合併的**前提是 file-contiguous**，而：
1. 一個 expert 的三段相隔 **88~115 MB**（§EN-1330）⇒ 跨段不能合併；
2. 只有**同一 kind 內、檔案相鄰的 expert**（stride 139,264 B）才連續；
3. 而 miss 的 expert id 是 **routing 的離散輸出** ⇒ 相鄰機率低。
⇒ 純 demand 的口徑已經是 **4.41 ≈ 3**（三個 segment 各一 job，合併基本到位）
⇒ **剩下的空間只有 4.41 → 3，即 job 數 −32%。**

量化到 t/s：fill 佔 step ~9%（§EN-1331，10:22 的生產口徑 nofill 臂會直接驗證）
⇒ **收益 ≈ 9% × 32% ≈ 2.9%，低於 3% 門檻** ⇒ 這才是 3b 不值得 rebuild 的量化理由。

### (e) 結論
方向（batch 化）**對**，但：**已做 + 機會被幾何鎖死 + 收益 ~2.9%**。
要再往前只能「主動多讀鄰居 expert 把 run 撐長」，那就是 neighbour prefetch ——
**已撤回**（位元組 1.98×，M-PF）。

## §EN-146x：「swap 衝到 5 GB」是**正常 macOS 行為**，三條證據排除 leak（23:2x）

問題：跑一輪 llama 後 swap used 從 0 → 5000 MiB，退出後 wired 回基線、swap 卻留著 —— 是不是 bug？

### (a) 三條「不是 leak」的實測證據
1. **swap_used 會自己降**：`Backup/p0attrib/summary.json` 有一筆 `swap_growth_mib = −91.0`
   （p012 臂 5722.25 → 5631.44）⇒ 回收確實發生。
2. **今晚 idle 漂移**：23:20 **3554.56** → 23:22 **3450.56** → 23:27 **3402.56** → 23:28 **3402.56**
   （llama procs = 0 全程）⇒ 惰性回收在做事，7 分鐘 −152 MiB，之後 plateau。
3. **重開機後 swap 起跑 = 0** ⇒ 沒有跨 session 的永久佔用。
4. wired 每次都回基線（22:59 那輪 12363 → 1654；idle 時 1827 MiB）⇒ 退出就釋放，沒 leak。

### (b) 機制定性（可引用）
16 GB 機器上引擎 wired ≈ 12 GB ⇒ 桌面只剩 ~4 GB ⇒ macOS 必然把桌面的 inactive 匿名頁換出。
**頁是別人的，成因是我們。** 退出後 swap 留著是 macOS 不主動回收 swap 空間（空間會被重用），
跟洩漏無關。

### (c) 一夜下來單調上升是「回收跟不上推擠」，不是 leak
每臂 `swap_growth_mib` = +476 / +681 / +1106 / +1515 / +1723 / +1850 / +1957 MiB（唯一負值 −91）。
鏈式相接（4207→5722→5631→6313）可看出**每條都 +幾百 MiB 往上疊**，而回收只有 ~0.4 MiB/s 量級
⇒ 420 s 冷卻遠補不回來。**swap file 自己也長大**（total 5120→6144→7168 MiB）＝ 持續 pressure 的直接證據。

### (d) ⚠ 但有兩件事「不正常」，而且都在傷我們
1. **min_free 掉到 14.1 MiB**（`Backup/eseries/E2b|E4/summary.json`）、15.3（E2_s1）、47（E2_seg）
   ⇒ **接近 jetsam 區**，OS 會開始砍行程；今晚 `wired_probe` 兩臂的 `Insufficient Memory` abort
   就是同一 pressure 的另一端症狀。
2. **量測污染**：跑動中 `pageins` 達 **12266/s**（E2_seg driver.log），而 expert pool 本身也走 SSD
   ⇒ 被擠出去的鄰居醒來後直接跟我們搶頻寬。這就是契約 §3.3 `2048 MiB` 門檻存在的理由，
   也就是今晚 8/8 臂全踩污染門的原因。

### (e) 結論
**OS 層面：正常，不用修。** **Rig 層面：16 GB 上跑 8 GiB 常駐池 ＋ 兩個桌面 session 是設計缺陷。**
要解的題是「pool budget 政策」，不是「swap」。手段：(1) 例外測試卡縮小 pool（1/2/4 GiB 多點）；
(2) 或換到沒有第二個 user session 的乾淨盒。

### (f) 儀器坑（下次別踩）
- `vm_stat` 的 key 是 **首字母大寫**（`Pageins:`），小寫比對會靜默全空 ⇒ parse 一律 `.lower()`。
- `memory_pressure` 回報的 `System-wide memory free percentage: 85%` 與 `vm_stat` 的
  `Pages free 131 MiB` 差很多（前者計入 file-backed／purgeable）⇒ **不要引用它的百分比**，
  要講可用量就用 vm_stat 的 free＋speculative＋inactive。
- harness 的 swap 欄位是 **`swap_before_mib` / `swap_after_mib` / `swap_growth_mib`**（不是 `swap_used_mb`）。
