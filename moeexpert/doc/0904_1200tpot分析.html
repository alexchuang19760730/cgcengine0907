④ residual 長條圖更新：draft sampler 已定位到 sync wait

這一輪不再只把 residual 寫成「CPU split / sampler / KV / 其他」，而是把 common_speculative_impl_draft_mtp::draft() 與 common_sampler_sample() 真正拆到函式級別。結論是：draft sampler 幾乎不是 grammar / backend chain 問題，而是 llama_synchronize(ctx_dft) 等待 async draft decode 完成。最新 async/sync 邊界 telemetry 更進一步證明：decode_iters = first_after_decode = sampler_calls，且 gap_after_decode ≈ 0，也就是每一次 sample 幾乎都是在上一個 llama_decode(ctx_dft) 提前返回後立刻進同步。

因此，residual 的最新口徑不該再寫成寬泛的「sampler / KV / 其他」，而應該明確更新成：draft sampler sync wait 才是 server-core residual 裡最大的可改子桶。這也直接回答了「MTP draft 路徑是否有額外開銷」：有，而且幾乎全部表現為 sample 前的同步等待。 更細地說，現在已可寫成：common_sampler_sample() 並沒有做重 CPU 工作，而是在每次 draft decode return 之後立刻被迫同步 GPU 尾段。

⑤ 最新 legacy-25plus 槓桿更新

這裡直接用 CPOT 白皮書已經做過的實驗，把 legacy 線上哪些槓桿仍然打得開、哪些已經關閉，重新整理成可執行結論。

槓桿現況對 legacy-25plus 的意義是否繼續追
LAYER_CAPS（40-40:256） 白皮書已證明 miss -77%、hit +35.5pt、thrash 穩態約 +0.8 t/s 這不是候選優化，而是 legacy 健康線的必要基線；一旦拿掉，draft layer residency 會退化。 保留
MMV_FUSE 白皮書 A/B：bit-identical，暖配對約 +0.15 t/s（+0.6%） 收益小，但乾淨、便宜、沒有額外語意風險。 保留
routing-aware placement / oracle pin / LFU 類 白皮書已定案：verify cold 幾乎不動，root cause 是時序錯位而不是 resident-set 放置 這一族槓桿對 legacy 線已基本關閉。 關閉
fused-down 白皮書定案：結構上 wash-to-loss，且 carrier 路徑不完整 不值得再投入時間。 關閉
verify wait / GPU 依賴鏈縮短 fresh 直接量測後，仍是最大桶：67% ~ 74% wall 如果 legacy 要從 26.3 再往 30+ 推，幾乎只能從這裡吃時間。 主開放槓桿

⑥ 依 CPOT 規則，legacy-25plus 離 30+ 還差什麼？

現在基準線已不是 14.5 t/s 的 debug 狀態，而是 26.31 t/s 的健康 longform 線，所以要到 30+ 並不是遙不可及的大修，而是要再吃掉 4.68 ms/token。

槓桿預估收益依據備註
再縮 verify wait / GPU 依賴鏈 -3.5 ~ -5.0 ms/token fresh 量測已證明 verify wait 仍是最大桶；要往 30+ 只能繼續從這裡拿 這是唯一仍對得上 CPOT 分桶的主槓桿。
在 legacy-25plus 線上重 sweep n_max / batch / ubatch -2.0 ~ -2.5 目前 longform benchmark 線已乾淨，適合做不混 QA 的純性能 sweep 這是 server 端最務實的下一輪對照實驗。
維持 LAYER_CAPS 與 MMV_FUSE 全開 基線已吃到 這兩刀是 legacy 健康線已知有效收益 不是新增槓桿，但絕對不能回退。
壓 residual（已定位為 draft sampler sync wait） -1.5 ~ -3.0 fresh 量測顯示 residual 仍占 21% ~ 28% wall；而最新 telemetry 已把其中最大的 server-core 子桶定位到 common_sampler_sample() → llama_synchronize(ctx_dft) 優先度仍低於 verify wait，但這一刀已經從「廣義 residual」收斂成「draft sync wait」。
placement 類（LFU / pin / routing-aware） ~0 白皮書已反證這一族槓桿對 verify cold 無實質改善 不該再投入時間。
wrapper / JSON / HTTP 微優化 < -0.7 當前 legacy 還快於 CLI，wrapper 尚未暴露成主瓶頸 可做，但順序必須排後。

換句話說，現在要到 30+ 的最短路，不是回頭追 wrapper，也不是重開 placement 分支；而是先壓 verify wait，再補看 residual 裡的 CPU split / sampler / KV。這是 fresh 直接量測後的新排序。

  • longform benchmark 固定走 legacy-25plus；
  • 在這條線上重跑 n_max / batch / ubatch 的純性能 sweep；
  • 下一輪若要再細拆，就應改成對 residual 做更細的 CPU-side telemetry，而不是再爭論 wrapper。

⑧ Windows 端如何連上我們的 server

目前 server 已經提供 OpenAI-compatible 介面。Windows 端不需要懂 llama.cpp 內部細節，只要把 Base URL 指到 Mac 上的 /v1 就可以。

項目說明
Base URLhttp://<Mac LAN IP>:8080/v1 或你實際啟動時指定的 port，例如 http://192.168.101.87:8099/v1
Chat CompletionsPOST /chat/completions
ModelsGET /models
Auth目前本地 LAN 測試線不需要 API Key；若上外網再另外補保護。
# 先在 Mac 上啟動 server
CGC_SERVER_MODEL_ROOT=/Users/alexchuang/Documents/flashkv0516/models/gguf \
CGC_SERVER_PROFILE=legacy-25plus \
CGC_SERVER_PORT=8080 \
bash scripts/run_server.sh

# Windows PowerShell 測試：列出模型
Invoke-RestMethod -Method Get `
  -Uri "http://192.168.101.87:8080/v1/models"

# Windows PowerShell 測試：chat.completions
$body = @{
  model = "test"
  messages = @(
    @{ role = "user"; content = "請用一段中文說明巴黎為什麼是法國的政治與文化中心，避免條列，至少120字。" }
  )
  temperature = 0
  max_tokens = 220
  stop = @("<|end|>", "<|output|>", "<|user|>")
} | ConvertTo-Json -Depth 6

Invoke-RestMethod -Method Post `
  -Uri "http://192.168.101.87:8080/v1/chat/completions" `
  -ContentType "application/json" `
  -Body $body
  • 若 Windows 端連不上，先檢查 Mac 的防火牆是否允許該 port，並確認兩台機器在同一個 LAN。
  • Mac 本機自測 localhost 時要加 --noproxy '*'；Windows 對 LAN IP 通常不需要。
  • 若要給第三方 SDK（OpenAI SDK、LangChain、LobeChat 等）接，只要把 base URL 改成這個 /v1 即可。
