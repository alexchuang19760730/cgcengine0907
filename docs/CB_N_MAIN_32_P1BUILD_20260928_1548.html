2. 機制假說：它動的是「時間軸」，不是工作量

ggml_metal_graph_compute 每次開 n_cb + 1 個 command buffer；最後一個 （slot n_cb）由呼叫執行緒序列編碼節點 [0, n_main)，其餘由 worker 並行編碼剩下的。 n_main 的預設是：

const int n_main = cgc_cb_nmain != NULL ? MAX(1, atoi(cgc_cb_nmain)) : MAX(64, 0.1*gf->n_nodes);

09-26 的桶分解（docs/CB_N_MAIN_BUCKETS_2026-09-26.md §3–§4）與這個機制一致： submit −23.0%、cb 只有 −3.3%（噪音內，因為 cb 是 gather， 與編碼切分無關）、大頭落在 wait（−6.80 ms）。

9.1 處置

  1. 不改 scripts/run_server.sh 的預設值（CGC_CB_N_MAIN 維持 unset ⇒ upstream 行為）。 這是本輪唯一會動到別條線的動作，缺乏支持證據時不做。
  2. n_main 對數值中立（§3）可以引用 —— 它是本輪確定下來的成果。
  3. 若要定案：在乾淨窗重跑同一組 ABBA；若 rep1 差異仍 <3% ⇒ 按 on_fail 登記判死、從待辦移除。

10. 誠實邊界：這一份不主張什麼

  • 不主張 n_main=32 沒有增益。只主張「增益 ≤3%」（rep1 層），且是在髒窗下。
  • 不主張 09-26 的 +12.8% 是錯的。它可能真的存在於那顆 binary 上、或真的存在於乾淨窗裡。本輪只是沒看到。
  • 不主張任何 TPOT 分解或分段拆解（§7、§8 全部標「本輪未量測」）。
  • 不主張 wait 的縮減來自 gap —— union/gap 未拆（§8 黃框）。
  • 未跑：CGC-DECPROF、CGC_GPU_TIMING、{16,64,128} 掃描、乾淨窗 ABBA。
  • 未做：索引重生（agent_harness/ 有別條線未提交的改動，重生會吸收對方位元組； 且本 commit 的兩個新檔都不在 MANIFEST.jsonl 的掃描範圍內 —— scripts/check/charters/ 在 manifest 中命中數為 0）。
  • 技術子目標：本槓桿既不動 41 段提交的同步（S）、也不動 MTP（M）⇒ 不適用； 立項卡自己的子目標是 sg-cbnmain-submit（submit −23%，本輪未複測）與 sg-cbnmain-tps（+8%~+13%，未達成）。
