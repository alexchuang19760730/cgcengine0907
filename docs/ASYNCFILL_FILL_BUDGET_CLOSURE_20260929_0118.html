2. ⛔ 三個計數器都不能拿來算 fill

計數器為什麼不能用
pread_us nofill 臂 read_mib=0 卻 pread_us=375–556 s ⇒ 它計的根本不是 fill，是別的 pread（模型權重／mmap 頁入）。 誤用會得到「每次 miss 52–95 ms」——比真值大兩個量級。
fill_wait_us 只覆蓋 ensure_slot（同步單 slot）路徑；本 cell 走 ensure_batch（L3 Option A）⇒ r1/r5 為 0、r4 整趟僅 154 ms ⇒ 不是 fill 總耗時。
EBTIMER step_usec 窗口跨段：同一份 log 裡 n_sum/41 既有 8.00（純 decode） 也有 14.9–21.3（混 prefill）⇒ 一行既可能是一步、也可能是一段。

⇒ 「fill 占多少 ms/step」至今沒有任何可信實測。這是本線目前最大的未量量。

3. 「34.5 ms」的物理含義

34.5 ms ≈ 17.3 MiB @ ~0.5 GB/s，與「同步 fill、有效吞吐 ~500 MB/s」自洽 （不是 SSD 峰值：pool 頁在 swap、隨機讀、單執行緒 pread）。 ⇒ 落點區間的跨度其實來自「fill 實際有效吞吐」這個未知數：

4. k = 8 的論證修正（method_culpa #2）

上一節用 328 / 41 = 8.000 解出 k —— 除法對，理由錯： 源碼 llama-expert-cache.cpp:~1195 的 fprintf 第 4 個參數是 nl（slot_owner.size()）⇒ calls 恆等於 41，不是觀測值。

  1. flush 條件 calls % nl == 0 ⇒ 每個窗口確實含 nl 次 ensure_batch；
  2. 其它窗口 n_sum/41 = 14.9–21.3 ⇒ prefill 段每次呼叫 n ≈ 18；
  3. 若 328 窗口混了 x 次 decode(n=8) 與 41−x 次 prefill(n=18)： 8x + 18(41−x) = 328 ⇒ x = 41 ⇒ 純 decode、每次 n = 8 ⇒ k = 8；
  4. n_layer = 41 由趟末統計行 n_layer=41 獨立證實（非由 calls 推得）。

⇒ 結論保住、論證換掉；J2 = 328 op/step 不變，J1 不依賴 k 故不受影響。

5. 給線 I 的工單（本線不動 src/）

修 EBTIMER 的價值 = 把上表的「有效吞吐」從未知變成實測（跨 12.9 → 19.4 t/s）。 位置：src/llama.cpp/src/llama-expert-cache.cpp，cgc_eb_timer（1159-1195）。

  1. calls 欄位現在印的是 nl（恆 41）⇒ 改印實際累積呼叫數，或改名 nl=；
  2. 窗口邊界改成 step 邊界（calls % nl == 0 讓 prefill／decode 共用同一個累加器） ⇒ 帶 step id 或由呼叫端顯式 flush，見證行加 seg=；
  3. pread_us 改名（它不測 fill）。
