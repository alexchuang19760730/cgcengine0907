# CGC Expert Cache 整合差異分析 (2026-09-05) ## 0. 結論先講 **Dev branch 3 個 commit 之前已 cherry-pick 到 devserver,但全部被 revert** (commit `80939f844` / `e3af2992f` / `a7d176394`)。Revert 原因是 **直接合併會把 26+ t/s 的 GPU pool path 打成 5.5 t/s 的 CPU resident path** —— dev branch 走的是「放棄 pool 保正確」,跟我們「保留 pool 求速度」的策略**互斥**。 但 dev branch 仍有些**可借鏡的局部修補**可以採納 (見 §4)。 --- ## 1. 為什麼 devserver (我們) 快: 26+ t/s 的核心機制 ### 1.1 動態 slot table (256 → 87 對映,無 0000 風險) - `expert_cache_on_topk` (llama-context.cpp:3033-3360) - **256 expert 永遠有效**: `hparams.n_expert = 256` **從未被縮** - `slot_table[il][e]` 動態記錄每個 expert 對應的 pool slot - hot (在 pool 內): 0..n_slots-1 - cold (不在 pool): **-1 → 指向 ZERO-slot** (zeroed 過的固定槽) - 跟 dev branch 不同: devserver **不修改 `ne[2]`**,tensor 仍是 256 expert 完整形狀 ### 1.2 GPU 4GB Pool + 統一記憶體 - `expert_cache 4294967296` (4GB) 配置下, hot experts 永遠 resident - `process_ubatch` 從 disk pread 進 pool (async),decode 命中就直接讀 - 16GB Mac 的 unified memory 讓 CPU/Metal 共用同一份 buffer ### 1.3 MTP Fast Path (CGC_VERIFY_DECODE / CGC_DRAFT_DECODE) - llama-context.cpp:3189-3268 - **Warm gate** (`CGC_WARM_NPAST=256`): prefill 餵飽 pool 前走 ensure_batch,餵飽後走 fast path - Fast path 只 touch + zero slot, **不做 pread**, 所以 65% cold 仍能 26+ t/s - Cold 走 ZERO-slot (固定 0 權重槽),但 softmax 吸收 < 1/3 cold 不影響 routing ### 1.4 Layer 0 Identity Remap (L4_SKIP_LAYER0) - llama-context.cpp:3158-3169 - blk.0 是 full-weight CPU skip-load tensor,**不走 pool** - 寫原始 expert ID (identity) → mul_mat_id 讀原始 tensor 完整 256 expert --- ## 2. 為什麼 dev branch 正確: 5.5 t/s 但語意對 ### 2.1 Root cause (522428cdc / 1afedfa68 共同根因) - dev branch 的 **pool 設計缺陷**: - Pool 是 zero-copy (adopt from tensor buffer),repointing 是 no-op - 載入時把 tensor `ne[2]` 從 **256 縮到 87** (pool capacity) - Expert >= 87 **直接 OOB 或被當 slot 0 (零權重)** - 結果: layer 2+ uniform routing [0 1 2 3 4 5 6 7] → 0000 garbage ### 2.2 Dev branch 修法 (1afedfa68 核心) - llama-context.cpp (line 3659 改前 / 3611 改後) - **改前**: `if (!pool_active || model.expert_cache_skip_load)` → identity remap - **改後**: `if (model.expert_cache_skip_load)` → identity remap - 也就是: **完全不走 pool**,所有 expert 從 CPU 原 tensor (ne[2]=256) 讀 - 結果: 5.5 t/s (CPU 頻寬瓶頸) + 語意 100% 對 ### 2.3 為什麼 dev branch 5.5 t/s (不是 26+) - 放棄 4GB GPU pool,所有 expert 走 CPU - 16GB Mac 上 256 expert 完整大小 = ~12.5GB (over budget) - 強制 unified memory CPU path,沒有 pread 預熱 ### 2.4 為什麼 dev branch 還能正確輸出 - Identity remap (real expert IDs 0..255) 讓 mul_mat_id 從原始 tensor 找 - Metal 透過 unified memory 讀 CPU tensor (慢但對) - 所有 41 層 256 expert 都能路由,gate logits 不退化 --- ## 3. 兩邊的本質差異 (不是 bug,是設計哲學) | 面向 | devserver (我們快) | dev branch (他們對) | |------|--------------------|--------------------| | 256→87 對映 | **動態 slot table** (e → slot, cold = -1) | **靜態 ne[2] shrink** (tensor 硬縮) | | 冷專家處理 | **ZERO-slot** (固定零槽) | **沒概念** (直接 OOB) | | Fast path | **CGC_MTP_FAST** + warm gate | **沒有** (一律 ensure_batch) | | n_expert tensor 形狀 | 維持 256 | 縮到 87 | | 4GB pool 命中率 | 35% (cold ZERO-slot 吸收) | 不適用 (放棄 pool) | | 速度 | 26+ t/s | 5.5 t/s | | 語意 | 條件性對 (zero-slot 過多時退化) | 100% 對 | **核心矛盾**: -
