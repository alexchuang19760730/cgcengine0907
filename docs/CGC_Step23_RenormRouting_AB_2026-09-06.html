CGC Expert-Cache Step-2a / Step-3 Renormalized Routing — A/B 驗證報告

日期：2026-09-06　分支：devserver　模型：Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X（ngl=99 + expert-cache 4GB + MTP）

1. 背景

Step-2/3 的目標是讓 decode 在「expert cache 的 ZERO-slot fast path」下不損失語意品質，最終把速度拉回 25+ t/s：

  • Step-2a（produce）：在每層 top-k hook 前，從被 dispatch 的 topk 節點往上溯源找到該層 ffn_moe_logits* tensor，host 端 softmax 後計算「冷 expert 的加權路由質量 / 總質量」，寫入 cgc_weighted_cold_ratio[il]。
  • Step-2b（consume，先前 commit 5e3d4df9a）：fast-path cold guard 改讀加權冷比率（非 1e9 哨兵時），count-based 只作 fallback。
  • Step-3（renorm）：router softmax 前把冷 expert（slot_table<0）的 logits mask 成 −inf，softmax 重新歸一化到 resident experts，冷 expert 不可能被 top-k 選中 → ZERO-slot 不再污染。

4. 分析（誠實版）

4.1 為什麼「weighted guard 單獨開」會讓 coding 從 1.0 掉到 0.3？

weighted 比率比 count 更「寬鬆」：某層 union 有 20/32 冷 expert（count 62% > 30%，count guard 會擋下 fast path），但若這些冷 expert 只扛 20% 路由質量（weighted ≤ 30%），weighted guard 會放行 fast path → 冷 expert 的 ZERO-slot 貢獻變成 靜默丟失 ~20% 路由質量（softmax 未重新歸一化）。IQ3_XXS 對這種質量的丟失很敏感 → 確定性迴圈。這證明：沒有 renormalization 時，count-based 才是正確的保守選擇；weighted guard 的價值只在搭配 Step-3 時才成立。

4.2 為什麼「weighted + renorm」速度達標（25.5 t/s, 96% accept）但 coding 品質仍壞？

速度證明 mask-leaf 機制與 25+ t/s fast path 相容（無同步 ensure_batch，MTP accept 96%）。但品質壞在 pool 成員與真實 routing 不匹配：

  • 層 0 永遠 warm=0（debug：CGC-RN-FLOOR: il=0 warm=0 < k=8）→ floor 把 mask 全清 0 → 層 0 走 ZERO-slot/guard 路徑。
  • 層 1+ warm 恆為 70/256：這 70 個 = loader 依序 prewarm 的 expert 0..70，而模型真實偏好高 ID expert（如 193/233/249）。renorm 把真熱 expert 全 mask 掉 → 模型被迫在 70 個「錯的」expert 間路由 → 0/1 振盪。

換言之 renorm 讓品質「優雅地」退化成「一個只剩固定 70 expert 的模型」——如果那 70 個不是該 prompt 真正需要的 experts，輸出照樣壞。要讓 renorm 有好品質，pool 成員必須跟著真實 routing 走（decode 驅動的 hot-set prewarm / 每層 ensure 的持續生效 / 或讓熱 expert 在 softmax 前就已 resident）。這是下一里程碑（pool membership 修復）。

6. 最終判定（數據定案）

16GB + ngl=99 + 4GB expert pool（71 slot/層）下，「renorm + 25+ t/s + coding/longform 品質 ≥ baseline」不可兼得。原因是 capacity-bound 而非 membership 選擇：現況 membership 已達 74.8% ≈ 事後完美 top-71 的天花板 76.4%。71 slots 天生只能承載 ~3/4 的 routing mass，renorm 在 softmax 當下無可避免地丟掉 ~24%（mask 在 step 開頭寫入、guard 的 ensure 在層 softmax 之後才補槽，同一 step 補不回來）。

hybrid 原型失敗的機制：mask 在 step 開頭寫死，guard trip 的那一步（本應 exact）softmax 已被 mask 排除真熱 experts → 同一步補不回 → 全 profile 品質崩潰。結論：renorm 的 mask 必須在「該層 softmax 前」membership 就已正確，這要求 resident 集合在 decode 前就貼近該 prompt 的真實 routing —— 而 71 slots 的 mass 天花板只有 ~76%。

7. 可行路徑（供決策）

  1. 加大 pool（唯一能讓 renorm 到 25+ 的路）：K=128 → ~7.3GB、K=192 → ~11GB expert budget（mass 覆蓋 93%/99%），16GB 機在 ngl=99+MTP 下會 OOM → 需要 32GB 硬體再測。
  2. 16GB 上維持現狀：預設 config（baseline 品質 1.0/0.882/1.0，7–14 t/s）；若要更快，可先試「非 renorm」的小步優化（如 reduce guard trip 次數的非同步 prefetch 調校）。
  3. 層 0 warm=0 為設計使然（skip-load full-weight），不需修。

本 commit 的 CGC_MASSCOV 儀表可供日後在 32GB 機上直接量測驗證。
