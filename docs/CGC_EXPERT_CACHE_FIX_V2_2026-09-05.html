CGC Expert Cache 修復說明書 v2

日期: 2026-09-05  |  分支: dev  |  模型: Qwen3.6-35B-A3B (IQ3_XXS + denseIQ4X)

一、問題摘要

Expert cache 在 ngl=99 時產生 0000/garbage 輸出。根因分析:

1.1 Pool 路徑的根本問題

發現: Pool 路徑的 repointing 是 no-op — pool 是 zero-copy（從 expert tensor buffer adopt），所以 wt->data = pool_base 實際上不改變任何東西。ne[2] 被 shrink 到87（pool capacity），但模型有256個 experts。當 gate routing 到 expert ≥ 87 時，slot 0 被使用（零權重）→ 退化。

1.2 根因鏈

模型: 256 experts, top-k=8
Pool: 87 slots (budget=4GB / 41 layers / 1.2MB per slot)
ne[2]: shrunk from 256 → 87
Gate routing: expert 0..255 → remap to slot 0..86
Expert ≥ 87: maps to slot 0 → zero weights → degenerate gate logits
Result: layer 2+ uniform logits [0 1 2 3 4 5 6 7] → garbage output

二、修復方案: Resident Passthrough

方案: 當 expert_cache_skip_load=true (ngl=99) 時，expert tensors 保留在 CPU，ne[2]=256（不 shrink），使用 identity remap（real expert IDs 0..255）。Metal 從原始 full-size tensor 讀取。

3.3 Pool 路徑分析（未修復）

結論: Pool 路徑在 ngl=99 無法正確工作。原因:

  • Pool 是 zero-copy（adopt from tensor buffer），repointing 是 no-op
  • ne[2] shrink 到87 < 256 experts → expert ≥ 87 maps to slot 0
  • 需要256 slots 才能覆蓋所有 experts，但 256 × 1.2MB × 41 layers = 12.5GB > 16GB Mac

五、已知限制

  1. 16GB Mac 限制: 256 experts × 41 layers 無法全部放在 GPU pool 中。需要32GB+ Mac 或減少 expert 數量。
  2. CPU bandwidth 瓶頸: Resident passthrough 讓 expert tensors 在 CPU，Metal 透過 unified memory 讀取，速度受限於 ~3.4 t/s。
  3. MTP + ngl=99 OOM: MTP draft context 額外需要 ~2GB GPU 記憶體，在16GB Mac 上 OOM。
  4. Server API expert_cache_active=0: Server 路徑可能未正確啟用 expert cache，需要進一步調查。

六、下一步

  1. 32GB+ Mac: Pool 路徑可以工作（256 slots × 1.2MB × 41 layers = 12.5GB，32GB Mac 可以容納）
  2. 減少 expert 數量: 如果模型支持，減少 n_expert 到128或更少，讓 pool 容納所有 experts
  3. Server API 修復: 調查為何 server 路徑 expert_cache_active=0，確保 OpenAI API 正確使用 expert cache
  4. 速度優化: 在 resident passthrough 基礎上，透過 prefetch、warmup、減少 overhead 提升速度
