# `--spec-draft-n-max 3` was really k_eff = 1 — root cause, fix, acceptance

**Date** 2026-09-26 · carrier Nail-Qwen3.6-35B-A3B-MTP IQ3_XXS-denseIQ4X (`qwen35moe`,
`nextn_predict_layers = 1`, read straight out of the GGUF header) · prof `prod-new`

## 0. One line

`--spec-draft-n-max 3` reached the engine (bench banner `draft n_max=3`), the MTP impl's cap was 3,
and **the draft loop still produced exactly one token per round** because its *second* step decoded
at a position the shared KV already held: `llama_decode` refuses it (M-RoPE needs `X < Y`, the log
shows `X = Y`), the loop `break`s, and `k_eff = 1` — silently, on the bench **and** on
`llama-server`. The trigger is the `is_mem_shared` batch layout, which commit `65c76b8c7`
(2026-09-25 17:16, the `ctx_other` fix) switched on for this model.

## 1. The evidence chain (all from files, none of it inferred)

**(a) The flag arrives.** Bench stderr, both arms of the A/B: `llama-bench: [spec] draft-mtp enabled
(draft n_max=3)`. The per-call `-1` that llama-bench passes to the dispatcher is *not* the cap: the
dispatcher only truncates when `dp.n_max > 0` (`common/speculative.cpp:2839`) and the impl's own cap
is its member `params.n_max`, which comes from `params.draft.n_max` (`:1306-1308`, `:1820`).

**(b) The observed draft depth.** `SPECDBG round: … draft=` (`llama-bench.cpp:3023`):

| 2026-09-25 17:48 `spec_cost_en-mtp-repro` (k=3, ×3 reps) | `-p 0 -d 512` | 75/88/79 | `{1: all}` | **1** | (stderr not kept) |

**(c) The mechanism, verbatim from the log.** `Backup/cgc_logs/llama_server_20260926_000012.log`
(the *delivery* path, not the bench) printed this 64 times in one run:

```
E init: the tokens of sequence 0 in the input batch have inconsistent sequence positions:
 - the last position stored in the memory module of the context (i.e. the KV cache) for sequence 0 is X = 2873
 - the tokens for sequence 0 in the input batch have a starting position of Y = 2873
```

and the same run reported `draft acceptance = 0.46667 (7 accepted / 15 generated), mean len = 1.47` —
i.e. `mean_len = 1 + a` with `a = 7/15`, which is only possible with **one draft token per verify
round** (`verify steps ≈ 15 = generated`). The 09-25 03:26 server log (pre-`65c76b8c7`) derives to
`mean_draft = 3.002` and contains **0** `llama_decode[...]` lines. Same session, different server, same
model: the only difference is the commit.

**(d) The offending line.** `common/speculative.cpp`, draft-loop batch rebuild:

```cpp
} else if (is_mem_shared) {
    // note: with shared memory (e.g. Gemma4 assistants) we use the same position for all draft tokens
    common_batch_add(batch, id, dp.n_past, { seq_id }, true);      // ← same position every step
} else {
    common_batch_add(batch, id, dp.n_past + i + 1, { seq_id }, true);  // ← strictly increasing
}
```

`is_mem_shared` is `llama_get_ctx_other(ctx_dft) == ctx_tgt` (`:1413`). Before `65c76b8c7`,
`llama-context.cpp:155+` dropped `ctx_other` for every non-GEMMA4_ASSISTANT arch, so this model got
`is_mem_shared = false` and the **increasing** layout. The fix in that commit retains `ctx_other` for
`LLAMA_CONTEXT_TYPE_MTP` — correct for KV sharing, and it is what turned a latent layout bug into an
active one. `chain_heads` is `n_mtp_layers > 1 && !is_mem_shared` and this model has
`nextn_predict_layers = 1`, so it is `false` either way: **the position layout is the only thing that
changed.**

## 2. The fix (3 files, in the working tree, built — not committed)

1. `common/speculative.cpp` — split the two questions `is_mem_shared` was answering: KV sharing (unchanged)
   vs "all draft tokens carry ONE position" (assistant dialect only), via a new member
   `one_position_drafts`, set in the ctor as
   `is_mem_shared && llama_model_is_assistant_block(llama_get_model(ctx_dft))`; the loop's branch
   condition becomes `else if (one_position_drafts)`. A shared-KV **sequential** chain now takes the
   increasing-position branch, and the ctor prints one `SPC_INF` line saying k_eff must be read back
   from the round lines rather than assumed.
2. `src/llama-ext.h` — `LLAMA_API bool llama_model_is_assistant_block(const llama_model *)`, the single
   definition of the assistant allowlist that `llama-context.cpp` already uses.
3. `src/llama-model.cpp` — its implementation (`arch == LLM_ARCH_GEMMA4_ASSISTANT`).

**Why k=1 semantics cannot move:** at `k = 1` the loop hits `if (params.n_max <= (int) result.size())`
on the first token and `continue`s *before* the layout branch is reached, so the branch
(`one_position_drafts`) is unreachable and the k=1 draft token stream and verify batch are
bit-identical — the "push k_eff to k without changing output semantics" requirement holds **by
construction** for the only arm the oracle baseline uses.

## 4. Disclosed: one failure class survives, at step 0

Post-fix the remaining 11/76 failures are `llama_decode[0] returned -1`, same M-RoPE text with `X == Y`
at the *first* draft step. That is a different, secondary interaction: with a shared KV the draft's
first step re-anchors at a position the target already wrote (the bench's per-round re-anchor of
`id_last`; the server side may or may not share it). It costs the draft entirely for those rounds
(`draft=0` ⇒ E=1) — 14% of rounds here. It is *visible* now only because the fix restored multi-token
rounds. Any claim about this must come with its own histogram; it is not part of the k_eff fix.

## 5. Blast radius — what this invalidates

Any MTP-on reading whose source log contains `draft acceptance = … mean len = L` with
`L ≈ 1 + accepted/generated` (equivalently `generated ≈ verify steps`) is a **k_eff = 1** measurement.
From the on-disk census (`Backup/cgc_logs/**`, 8,291 lines parsed):

| log | mean len | accept | derived mean drafts/round |
|---|---|---|---|
| 09-23 13:27 | 4.00 | 1.000 | 3.0 |
| 09-24 09:47 | 2.16 | 0.385 | **3.0** |
| 09-25 03:26 | 3.63 | 0.876 | **3.0** |
| 09-26 00:01 | 1.47 | 0.467 | **1.0** |
| 09-26 01:21 | 2.00 | 1.000 | **1.0** |

and every bench artifact in that window: `spec_cost_en-mtp-repro-250925.json` measured
`m = 0.868`, `accept 0.62`, `E 1.45-1.71` **at k_eff = 1**. Those numbers describe a 1-draft
experiment; the `m = 0.868` that has been steering the MTP roadmap, and the "accept must reach 0.80"
target derived from it, have to be re-measured on a fixed build. The post-fix single-rep reading
(`m = 0.735`, one point, degraded box) is **not** a replacement — it is only proof that the number is
once again measurable.

Also note the commit message of `65c76b8c7` attributes `accept 0.98 → 0.44` to the ctx_other fix. That
comparison is confounded by this defect: 0.98 was measured at k_eff 3 and 0.44 at k_eff 1. The
honest statement is "the accept rate changed at the same time as the draft depth did".

## 6. The two acceptance items, run (2026-09-26 02:03-02:07)

### 6.1 Delivery side -- `k_eff` read back from the server, same cell, 45 s apart

Two `run_server.sh` launches (profile `prefill250`, MTP on). `k` is the profile's own resolved value,
read from the launcher rather than assumed: `CGC_DUMP_ENV=1 bash scripts/run_server.sh` prints
`ARG draft-mtp / ARG --spec-draft-n-max / ARG 3`, so nothing had to be passed in. Between the two
launches only the two dylibs differ (HEAD vs patched; checked by md5 and by the fix's own string).
Both were driven by `m123_oracle_gate.py`, so the probe, the env resolution and the teardown are the
gate's rather than a hand-built argv.

| arm | the server's own line | `spec draft: llama_decode[...] returned -1` |
|---|---|---|
| HEAD, pre-fix | `draft acceptance = 1.00000 (    1 accepted /     1 generated), mean len =  2.00` | 1 (`[1]`) |
| patched | `draft acceptance = 1.00000 (    3 accepted /     3 generated), mean len =  4.00` | **0** |

`mean_len = 1 + accepted` in both, so these are two different draft depths and not two different
accumulations: the pre-fix `2.00` is the same shape as the 2026-09-26 01:21 reading, the post-fix
`4.00` is the shape of the 09-23 13:27 / 09-24 09:47 readings (all three drafts accepted). The 09-26 00:01 reading of `1.47` is the same quantity at `a = 0.46667`. **The delivery path
now rounds at k_eff = 3.**

### 6.2 Oracle gate -- it does NOT pass, and the failure is inherited, not caused

The window ADMITTED at the gate's own default floor (no override): `reclaimable 10887 MB >= 8000`,
launcher probe 83% >= 40%, port 8080 free, zero foreign llama, thermal: no warning recorded.

| arm | M1 | M2 | M3 | rows | coverage | comparable |
|---|---|---|---|---|---|---|
| patched | **6/9** | 9/9 | 6/9 | 9/9 | 100% | yes (`config_diffs []`) |
| HEAD | 2/3 | 3/3 | 2/3 | 5/9 | 60% | yes |

* All three differing rows are `ctx=MTP` (the draft context's steps 2, 3, 4). **Every non-MTP row is
  bit-identical** to the reference (`row_hash_equal = 6`, `argmax_equal = 9`).
* The one MTP key BOTH arms emit -- `[2, 0, "MTP"]` -- carries the **same** row hash before and after
  the patch (`181c373a72e4a81c`), and differs from the reference (`e6afdbfbd03a0c6b`). The MTP-row
  numerics were therefore already off before this patch, and this patch does not move them.
* The patch does restore the reference's **row shape**: HEAD cannot even produce 6 of the reference's
  9 keys (`only_a = 6`) because at `k_eff = 1` the draft context decodes one token per round; post-fix
  the key set matches exactly (`only_a = 0`, `only_b = 0`).

Reading: the gate's verdict is **not a pass** (`ok = false`), so "oracle identical" is not established
for this cell -- the repo rule stands. But the failure is not this change's: it is inherited from the
same window that turned the draft chain into `k_eff = 1`. The claim "the k=1 path is untouched" is
confirmed in the form the baseline can express it (every non-MTP row bit-identical, plus the shared
MTP key unchanged), and the extra MTP rows the patch creates are exactly the ones the reference had.

Last full-coverage `9/9`: **09-23 11:32** (`summary_pfx-ckpt2.json`). First degraded: **09-25 17:09**
(`summary_en-mindmap-250925.json`, coverage 60%, M1 2/3) -- a shape that then repeats at 09-26 01:21.
The only spec-path commit in that window is `65c76b8c7`, whose diff contains the line that flips

### 6.4 A defect this run exposed in the gate's own provenance (found, NOT fixed)

The digest the gate's summary and the window-guard record carry **cannot distinguish the two binaries
just run**: `summary_keff_head.json` and `summary_keff_fix_win8000.json` have *identical*
`engine_digest` (same `libllama.0.0.279.dylib` `0cd5a628...`, same `libllama-server-impl.dylib`
`60fb7910...`, same `llama-server` `054fb22f...`), while the compare artifact of the same two runs does
separate them -- `libllama-common.0.dylib` = `2ac1cbb9cfcb` (HEAD) vs `87fab5907241` (patched).

The summary's set names a versioned `libllama` file the loader never opens (`libllama.0.dylib` ->
`libllama.0.0.578.dylib`, the `.279` file is a stale left-over) and omits `libllama-common`, which is
where `common/speculative.cpp` is compiled. Consequence: `m123_gate_window.py`'s `same_engine` check
would have called these two different engines the same, and any "this reading belongs to binary X"
claim on this line is blind to changes in the draft/spec code. Same class as the missing-md5 problem
already tracked for the other line. Needs the digest set rebuilt from the loaded files (resolve the
symlink, add `libllama-common`, drop the stale name) -- deliberately NOT done in this run, because the
gate's numbers were consumed above and changing its identity in the same breath would make them
unattributable.
