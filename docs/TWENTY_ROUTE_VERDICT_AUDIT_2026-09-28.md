## 1. K5：站得住（本表唯一一條）

`docs/K5_VERDICT_2026-09-21.md` 判 (C) 成立——那個「45.6 µs/節點」是**分攤恆等式**而非物理。
它的證據是三條**可複核**的東西：

1. **純讀碼**：`ggml-backend.cpp:2421` 的 `nsop_wns[q] += dur * ocnt[q] / owork;` —— 就是把每個
   command buffer 的時長**按節點數線性分攤**。
2. **儀器自證**：`uni` 欄（只含單一 op 的 buffer 的精確 µs/node）**44 種 kind 全部是 `-1.000`**
   ⇒ 從來沒有 buffer 只裝一種 op ⇒ 無從做精確除法。
3. **數值指紋**：同一步內 `CLAMP`(39)、`DIV`(39)、`GLU`(78)、`SUM_ROWS`(39)、`MUL_MAT_ID`(117)
   的 µs/node **恰好都是 52.05** —— 節點數差 3 倍、運算完全不同，小數後兩位相同。

⇒ 這是「算法恆等式」的證明，不是「某支臂比較慢」。**L2（+30~38%）作廢這件事沒有問題。**

> 但它**換來一個新靶**：61.3% 的 GPU 時間在每步 ~44 個「64 節點 command buffer」裡
> （`n_main = MAX(64, 0.1×n_nodes)`）。這個靶後來被 `n_main=32` 的 ABBA 撞過：
> `union −22.6%`、`busy −48.4%` 過檻，但 **`busy/union` 1.41→1.00** ⇒
> 「用段內並行換段間空窗，總時間守恆」⇒ 也關了。

## 2. (i) ρ/prebind：那個「+14%」是上界，而實測的基準是另一個輸出函數

`docs/RHO_MAXQ_SETTLED_2026-09-23.md` 的實測是：

| 臂 | t/s | hit% |
|---|---:|---:|
| base（**MTP off**＝交付口徑） | **9.85** | 94.9% |
| on（**MTP on**，無 ρ） | 9.21 | 67.9% |
| rho（無保險絲） | 4.62 | 88.9% |
| **rho-q16（MAXQ=16）** | **9.64** | 90.9% |

兩個問題：

1. **+14.0~14.5% 是白皮書的模型上界（`14.39 t/s`，`cb=42.04` 口徑），不是量測。**
   `GAP_FIX_EXEC §3` 自己寫著「白皮書 §6 那張敏感性表（33% → 13.53 … 100% → 16.01）
   **沒有一個 h 有實測支撐**」，而且 **h 與 ρ 量到的覆蓋率 0.854 是兩件事**
   （可以同時 `cov = 0.854` 而 `h ≈ 0`）。
2. **ρ 的 +4.7% 是對 `on`（MTP on）算的，而同一格的 base（MTP off）是 9.85 —— 比它快。**
   ⇒ 交付口徑的那個臂**本來就已經比 ρ 要打敗的那個臂快**。這與今天
   `MTP_CALIBER_REDEFINE` B4 的方向一致（OFF 中位 11.92 vs ON 7.34）。

⇒ **ρ 是「已 commit 的機制」（保險絲 `079f2fe46`、`#13 maxq_limit=3249/3348` 證明干涉是元兇），
但它的交付口徑淨增益沒有量過。** 引用時必須寫「MTP-on 基準下 +4.7%，絕對值因 swap 5768–6036 不可引用」。

## 3. (ii) M-S2：**「不可達」是誤引**（本節是本稽核最貴的一條）

`docs/S1_CORRECTNESS_SPEC_2026-09-26.md` §4 的表格寫：

> (ii) leaf 裝置化 … `CGC_SLOT_TABLE_GPU` 探針臂 576/576 正確但無速度主張；
> **M-S2「slot_table 裝置化讓 submit-ahead 合法」判不可達**

而實際來源 `docs/GAP_FIX_WHITEPAPER_2026-09-24.md` §4.C 說的是：

```
M-S2  ← 做法：把 slot_table 的發布搬到裝置，讓 CGC_SUBMIT_AHEAD=1 從「故意錯的探針」變成合法
       ⇒ 它拿掉的是 wait ＋ host 讀 ids ＋ 記帳，不是 fill 的 IO
       ⇒ 22.9（total→union）那端不可達；19.0（只有 submit 能搬）才是真上界
       ⚠ 分量相加在這個 regime 不閉合：gap ⊆ cb + submit 的交叉檢查以 10.09 ms 失敗
       ⇒ 現階段自評「上界 ≤ ~5%，且不可引用」
       §8 未閉合項：M-S2 的 19.0 與 B 的 17.36 口徑差未閉合；19.0 的推導過程未在本篇重建
       執行順序：4  M-S2（工程，上界 19.0，自評不可引用）
```

三個關鍵差異：

- **「22.9 不可達」≠「M-S2 不可達」。** 被否證的是「把 `total → union` 那 44% 全吃掉」那端；
  M-S2 自己的上界是 **19.0**，而它被留下的理由只是「分量不閉合（10.09 ms）＋ 推導未重建 ＋ 自評不可引用」。
- **它的狀態是「未動 ＋ 押後」**（`GAP_FIX_EXEC §4` 的順序表：「5 h ≥ 0.65 才做 A；**B / M-S2 押後**」），
  不是「已判不可達」。
- **候選表裡還有一條從未動工的 B（slot 間接化）＝ 17.36（+38%）**，做法正是
  「**ids 傳 slot index 而非 expert index，全鏈路無 CPU，41 段收成 1 段**」——
  **這與那支量到 22.2 t/s 的單段臂是同一件事的兩種形式**（模型 17.36 < 實測 22.22 ⇒ 模型低估）。

⇒ **S3／B 這條路是被一個引用壓住的，不是被一個量測壓住的。**

## 4. (iii) 便宜 hook：12.9 ms 是迴歸截距，而 F5 已判它不可移除

- `DECODE25_CEILING_2026-09-20` 的來源寫的是「每層 barrier **12.86 ms/step**（只要該層有 1 個 miss 就付）」。
- `CB_IS_THE_DEVICE_RESULT_2026-09-20` 的判詞表把它拆掉：

| 項 | 判詞 |
|---|---|
| `barrier 0.46 ms` | **a two-regime fit artifact**：迴歸把 queueing-curve 的質量塞進截距。直接殘差在同 3·m 工作是 **+0.16…+0.28 ms**（m≤4）、**負**（m≥6）⇒ 只判「**Partly — 6–13 ms/step total**」 |

- `MF5_BARRIER_ATTRIBUTION_2026-09-20`：**F5 REFUTED** —— 每層 barrier **不是**可移除的 overhead。
- `NEXT_MILESTONES_2026-09-27` 自己的追加：「12.9 ms 是 09-23 從 `cb` 反推的**常數項**，
  本 tree `src/` 裡**沒有 `barrier` 這個詞** ⇒ 它是**推算量不是插樁對象**」。

⇒ (iii) 的「上限 ~8%」是一個**由擬合截距推出來的數**，而那個截距已被判為 fit artifact、
其可移除性已被判否。**它不是一個可以動工的目標。**

## 5. 因此：20 的閘門現在長這樣

```
唯一在認可形狀上越過 20 的實測：單段提交 22.22（同 cell 同 build，ABBA）
      └─ 那條路 = S3 = 候選表裡的 B（slot 間接化，41 段→1）
            └─ 被判「無前提」
                  └─ 唯一依據：churn 42.3% —— 而它是 ntok=4（MTP-on verify）桶
                        └─ 今日口徑是 MTP off ⇒ ntok=1 主 context，那個桶從未被量過
      ⇒ 立項：scripts/check/charters/exp-churn-delivery-630.yaml（gate ok=True）
```

而與 20 平行的 shape／IO 那條線：絕對天花板 **20.49**（細切口徑）／**16.31**（舊 `gpu_sum`），
且 `18.59`（L3）**分母口徑錯**（用了非牆鐘的 `busy`），`union+gap` 地板在三個 run 之間是
**123.78 / 216.49 / 230.99 ms（1.75×）** ⇒ 那條線目前**沒有可信的單一天花板數字**。

## 6. 本檔不主張

- 不主張 M-S2 可取（它自評不可引用、推導未重建）。只主張它**不是被否證掉的**。
