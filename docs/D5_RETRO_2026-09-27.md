### 6.2 ★ 断点：`65c76b8c7`（09-25 17:16:09）并入的 `ctx_other` 修复

该 commit message 自称「docs(mindmap) …… 同批併入他線 src/docs/scripts 改動」——
**贡献者不是本线，本线只做定位、不主张归属。** 它并入的引擎改动共 4 档：

其中 `llama-context.cpp` 那 11 行是唯一的数值相关改动：

```c
// MTP draft contexts are CROSS-ARCH and identified by their context type, not by
// model.arch. They share the target context through ctx_other. The arch allowlist
// below only retains ctx_other for GEMMA4_ASSISTANT/EAGLE3/DFLASH, so every other MTP
// arch (e.g. qwen35moe) silently lost it here -> is_mem_shared=false (common/
// speculative.cpp:1413) -> the draft ran the non-shared catch-up decode instead of
// reusing the target context, and the accept rate collapsed (a 0.98 -> 0.44).
// Keep ctx_other for MTP contexts whenever it was supplied.
if (params.ctx_type == LLAMA_CONTEXT_TYPE_MTP) {
    cparams.ctx_other = params.ctx_other;
}
```

**为什么这一条正好只动 MTP。** 现状核对（`src/llama.cpp/src/llama-context.cpp:163-181`）：
保留 `ctx_other` 的原地只有三处阻段 —— `LLM_ARCH_GEMMA4_ASSISTANT`、`LLM_ARCH_EAGLE3`、
`LLM_ARCH_DFLASH`。除这三个 arch 外，MTP draft context 拿不到 target context ⇒
`is_mem_shared=false` ⇒ draft 跑**非共享的 catch-up decode**。而 `LLAMA_CONTEXT_TYPE_MTP = 1`
（`src/llama.cpp/include/llama.h:219`）。改动后 MTP context 一律保留 `ctx_other`。

⇒ 实测后果可预测、且与 §5.1 的数值分布完全同形：

| 探针位 | 属于哪条路径 | 受此改动影响 | 实测（v6 vs v7） |
|---|---|---|---|
| 6 个 `DEF` 位 | target 上下文的常规 decode | 否 | **逐字节相同** |
| 3 个 `MTP` 位 | MTP draft 上下文 | **是** | **全部不同** |

`65c76b8c7`（09-25 17:16:09）恰好落在 v6 档（09-22 13:49）与 v7 档（09-26 23:21）之间。

### 6.3 结论：**这不是回归，是一个上游性能修复进了版控**

v6 ref 记录的是「MTP 没拿到 `ctx_other`、draft 跑 catch-up decode」时的 MTP 数值；
v7 ref 记录的是修复后的。两点推论：

1. **D5 拿 v6 当基准 ⇒ MTP 三位恒定 FAIL**。那不是引擎坏了，是基准刻在修复前。
   §3 第 1 条因此从"不要用 v6"升级为"**任何以 v6 为基准的 M1 FAIL，在键名为
   `[2,3,4] MTP` 时可以一律判为基准迁移，不必再查引擎**"。
2. **改动注释自陈 accept rate `0.98 → 0.44`** —— ⚠ **本行 2026-09-27 02:2x 回改**。
   我原先读成「修复把 0.44 拉回 0.98、方向是变好的」，**那是反读**。原文文序是
   「*lost `ctx_other` → catch-up decode → … **the accept rate collapsed (a 0.98 -> 0.44)***」，
   `0.44` 是被描述的**当前（修复后）状态**：
