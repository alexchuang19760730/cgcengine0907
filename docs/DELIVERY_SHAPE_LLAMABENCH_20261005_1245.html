§1 問題：舊交付格在結構上交不出 prefill

原本的交付格 delivery 是 -p 0（pp-less）。它在測試卡裡是 §5.0 的唯一例外：沒有 prompt 那一列，就沒有東西去預熱專家池，於是它交不出 prefill，而「只報 decode」在 §5.0 明文是不完整產物、不可引用。看板自己早就記下了病根（C5 註記原文：「沒有 pp 那一列預熱池」）。

同時，歷史上的「decode 棘輪上限」15.210976（C13）是在舊預設形狀（-p 2048 -b 5632 -d 512 -r 3 --warm-skip 64）上量的 ⇒ 它與新形狀不可互比（§56），所以新形狀需要自己的基準線，而它此前在看板上沒有任何一列代表。

§4 柵欄 × 新形狀：兩方向配對 ＋ C14

CGC_OVERLAP_FENCE=41 從未在交付家族跑過（46/46 的柵欄產物都是舊格 p2048）。同一 invocation 各跑一次、ON 先後各一次：

趟OFF（prod-new）ON（+FENCE=41）比值
① OFF→ON10.689313.6641×1.278
② ON→OFF10.987613.7824×1.254
均值10.83813.723×1.266

順序無關：把 ON 放第一個跑，ON 仍 13.78、OFF 仍 10.99。四臂的 tg 逐 rep max/min 全部 ≤ 1.082，而臂間差 27% ⇒ 臂內離散比臂間差小一個量級。

⇒ 13.723 ≈ 舊形狀乾淨窗最高 C12 13.8674 ⇒ 換成 llama-bench 出廠形狀沒有損失速度。

C14：新形狀的柵欄值登記為「基準類」（不參與棘輪）

權威入口 caliber_certify certify 對這筆判 0/1 CERTIFIED，三個獨立理由：① R4（四臂全 attribution=swap）② 棘輪（13.66/13.78 ≤ 15.21）③ 下限（prefill 119.8 < 250）。放行 R4 也過不了棘輪那一條。⇒ operator 裁定走 ratchet_exempt（基準類）：新增 C14，棘輪上限 15.210976 不動。

D7 的 waiver 例外只放行 DIRTY（decode_board_build.py:1417；UNSTABLE 一律擋）。多臂 pair 檔必然 MIXED（冷的 OFF 臂 pp spread 1.374）；harness 的原生逐臂 json 是 llama-bench 原始輸出、缺包裝 ⇒ 閘門「判不了」。⇒ quote.artifact 指向 ON 跑第二趟（池已暖）那一臂的單臂產物（fence_on_cert.json，已驗 gate_verdict=DIRTY），與 C12／C13 的「quote 都是單臂」慣例一致。

§6 誠實邊界（不主張什麼）

  • 必備節 A（TPOT 分解）與 B（decode 分段拆解）本輪沒有新生產。本輪的交付物是口徑變更（形狀重定義 ＋ 一筆基準列），不是速度主張；新形狀（-d 0、warm_skip 0）目前連穩態都還沒到，此時做分段分解只會量到冷啟 regime。舊形狀的分段見 Backup/spec_tree/WAIT_ATTRIBUTION_2026-10-03.md —— 它不可搬到本形狀（§56）。
  • 所有 t/s 均不可引用：四臂／兩筆的 attribution 皆非 none（swap growth > 512 MiB）；pp 另有 spread > 1.10。凡引用須與「降級窗」一起講。
  • 棘輪上限不動：certify_anchor = 15.210976（cell (default)，指 2026-10-03 之前的預設形狀）。它是「已認證 decode 的最大值」，定義上只往上走；且與新形狀不可互比。C14 是基準，不是成績。
  • D5 數值那一半不適用：本 commit 0 個 src/。工作樹裡的 src/llama.cpp/src/llama-context.cpp（+17，純註解）與其 dylib 未納入本 commit（未重建驗證、未跑 D5）。
  • caliber_certify --selftest 33/34 是既存紅（用例「逐 rep max/min 1.107>1.10 ⇒ UNSTABLE」現回 QUOTABLE；all_spread > LIMIT and not split 在拆欄打開時不觸發）。已用 git archive HEAD 的暫存對照證明它在本輪改動前就是 33/34，非本輪引入。
  • 未跑 D5 的 m123_oracle_gate：本 commit 無 src/ ⇒ 該閘門對它沒有鑑別力（產物沒變，比的是同一份 binary 對同一份參考）。
  • 看板已重建（docs/mindmap/*）：它是從 decode_board_2026-09-29.yaml ＋ mindmap.json 機械生成；因而也重生了其他線節點的 brief（例如 L25-7／e-m2-slab-reuse）——那些節點的內容不是本輪寫的。
