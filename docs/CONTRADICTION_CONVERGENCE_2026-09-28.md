# 兩個矛盾的收斂：不是實測衝突，是引用錯儀器（2026-09-28）

狀態：**本文件零 GPU**。所有數字都是引用，來源逐條標出；只有一處是新算術（§3，且它只用既有讀數）。

---

## 0. 兩個矛盾的原文

**矛盾 A**：`m-decode25` 是 **tier 4（廢棄）**，`evid` 引
`DECODE25_FINAL_VERDICT_2026-09-21／DECODE_25TPS_VERDICT_2026-09-23／IO_AXIS_VERDICT_2026-09-25`。
但 `DECODE25_CEILING_2026-09-20.md` §7 在同一天**改寫了自己的判決**：
「~~25 數學上不可達~~ → 25 在當前的每 token 讀取效率下不可達 … **它是效率工程問題，不是物理限制**」。
⇒ 同一條結論被引三次，而三次的依據不同。

**矛盾 B**：`c-bandwidth`（tier 3a）說 dense GEMV 實跑 **56–108 GB/s**（DRAM 峰值 108.8），
而 `DECODE25` §7 說每 token 的有效率只有 **13.65 GB/s**（= 1.171 GB ÷ 85.8 ms，峰值的 11.4%）。
兩個數字不能同時是「事實」。

---

## 1. ★ 收斂：每一格的原話是它自己的儀器的話

| 讀數 | 儀器（原文） | 它真正量的是什麼 | **它不能被用來推出什麼** |
|---|---|---|---|
| **56–108 GB/s** | `dense_gemv_probe.cpp`：「單形狀 GEMV 探針。一個權重張量 + 一個 n 列輸入，反覆 `MUL_MAT` 計時。**不載入模型、不建 llama 圖、不開任何 `CGC_*` 儀器**」 | **一個 kernel 形狀的天花板**（微基準） | ❌ 模型每 token 的達成率。它沒有模型，沒有 MoE，沒有 per-token 路徑 |
| **13.65 GB/s** | 端到端 `1.171 GB ÷ 85.8 ms`（§7 的算術，不是儀器） | 整 token 的**平均**有效率 | ❌ 「kernel 沒吃滿頻寬」。平均值混了 kernel 執行、kernel 之間的縫、以及非記憶體成本 |
| **固定開銷 90%、收益 2.9%** | `io-shape`＋`IO_AXIS_VERDICT_2026-09-25`；`expert_file_layout.py` 7/7 | **pool 讀取形狀**（一個 expert 三段相隔 88–115 MB） | ❌ 整 token 的權重路徑 —— **E-A 實測那條路徑只佔 ~2%**（f ≈ 1.5%，`docs/S2_OVERLAP_EXPERIMENT_2026-09-28.md` §15） |
| **device busy：57% MoE／42% attention** | `c-device-span`（`DEVICE_BUSY_ATTRIBUTED_2026-09-23.md` §0/§1.1） | **最大一塊時間住在哪裡** | ❌ 槓桿。它自己的判詞：「歸因成立，但**不是可用槓桿**：受模型形狀與 kernel 物理約束」 |
| **0.0195%/dispatch（17.9 µs）** | `k3-price`（`K3_PRICE_MEASURED_2026-09-21.md`） | **邊際** dispatch 單價（平均值 45.6 已作廢） | ❌ **任何舊「融合能省 X%」的算術** —— 那一族已被此節點明文作廢 |
| **16.4% 未認證飄移** | `k3-swing`（`K3_PAIR_CERT_V2_BENCH_2026-09-23.md`） | k=3 的 1.43× 飄移的**認證狀態** | ❌ 任何比 16.4% 小的「還差多少」 |

**⇒ 矛盾 A 的解答**：`m-decode25` 引 `IO_AXIS_VERDICT` 當根據是**引錯根據**——那份判詞是關於
**IO 形狀**（pool 讀取），不是關於 25 的可達性；而 `c-device-span` 已經證明**最大一塊時間是
device busy**，不是 IO。兩者不衝突，因為它們回答不同問題；錯的是把它們當同一句話引。

**⇒ 矛盾 B 的解答**：**56–108 GB/s 是微基準，13.65 GB/s 是端到端**。兩者不衝突。
真正未知的是**兩者之間的倍差**，而它已被 `k3-price` 部分界定：dispatch 只佔 0.0195%/次
⇒ **倍差不是 dispatch 造成的**（要 ~35,000 次/步才能解釋 7×）。

---

## 2. 那個倍差是什麼（不新開儀器，只用既有判詞）

`c-device-span` 的判詞已經指名了：**「受模型形狀與 kernel 物理約束」**——
dense GEMV 是連續形狀（微基準量到峰值的 47–90%），
而 MoE 的讀取是 **256 選 8 的散佈式小讀取**（每 expert 的 ne11 很小）。
⇒ 這個倍差是 **shape penalty**，不是頻寬不足、不是 IO、也不是 dispatch。

**⇒ 三條「不是」都是既有節點已經量過的否定結論：**
- 不是 IO（`io-shape`：2.9% < 3%；且 E-A：那條路只佔 f≈1.5%）
- 不是 dispatch（`k3-price`：0.0195%/次；舊算術全作廢）
- 不是密集 kernel 的頻寬（`c-bandwidth`：打滿 100% 峰值也只省 2.42%）

## 3. 一處新算術：把 §7 的率放進 device-busy 那一格

用既有讀數（`S2_PROBE2` 的 E2b 暖：`total` 139.46 ms、`union` 104.87 ms、`mean_len` 2.40）：

```
每 token 的步時        = 139.46 / 2.40 = 58.1 ms   ⇒ 1.171 GB / 58.1 ms = 20.2 GB/s（峰值 16.8%）
只在 device busy 之內  = 104.87 / 2.40 = 43.7 ms   ⇒ 1.171 GB / 43.7 ms = 26.8 GB/s（峰值 22.3%）
```

**⇒ 即使在 device busy 之內，達成率也只有 ~22% 峰值**，而微基準的 dense 形狀是 47–90%。

**這就是矛盾 B 的量化收斂**：MoE 的散佈形狀把達成率從「dense 的 47–90%」壓到「~22%」，
而 §7 的 11.4% 是再乘上一次「非 device-busy 的 25%」的結果。**兩個數字都是真的，且不衝突。**

⚠ 假設：`mean_len` 2.40 與 E2b 的 `total`/`union` 同 run（`S2_PROBE2` 的算術自己就是這樣用的）；
`1.171 GB/token` 取自 §7 的 A3B × 3.12 bpw。**若 mean_len 真值是 16.4% 內的別的值，本節兩個率同比例平移。**

## 4. ★ 所以真正還開著的那一個量測：`k3-swing` 的 16.4%

**所有「還差多少到 25」的數字都小於 16.4%：**

| 數字 | 出處 | 大小 |
|---|---|---|
| S2 的誠實天花板 | §13（本 session） | **+8.7%** |
| 「最後 3.5% acceptance」 | portal | **+3.5%** |
| `io-shape` 的收益 | `IO_AXIS_VERDICT` | **+2.9%** |
| `c-bandwidth` 打滿峰值 | `DENSE_GEMV_INSTRUMENT` | **+2.42%** |
| **k=3 未認證飄移** | `k3-swing` | **16.4%** |

⇒ **在 16.4% 的漂移被配對認證關掉之前，「我們離 25 還有多遠」這個問題在度量上不可回答**——
每一個候選差額都在它的噪聲裡。`k3-swing` 自己的狀態：n=5 時 t=2.08 未達 df=4 的 2.776。

**⇒ 這就是那份「一次量測」：k=3 的配對認證，不是頻寬量測。**
而它正是本 session 已立的 `exp-caliber-calibration`（tier 3a，targets decode_tps 25.0）的
`sg-cal-refute` 子目標——**不需要新節點，需要把 n 加大到能認證為止。**

## 5. 本文件不能支持的

1. **零 GPU**：§3 的兩個率是既有讀數的算術，不是新量測。
2. **沒有改任何節點的 tier**：`m-decode25` 的 tier 4 與 `c-bandwidth` 的 3a 都維持原狀。
   本文件只指出它們的 `evid` 之間有引用錯位，**處置需要 owner 的判斷，不是本文的權限。**
3. **§3 的 22.3% 不是「MoE kernel 的天花板」**：它是在一個 mean_len 2.40 的步上，
   把整 token 的權重位元組除以 device-busy 時間——它是**一個混合量的上界**，不是任何單一 kernel 的效率。
4. **它不主張 25 可達**：它主張的是「擋住 25 的那些候選理由（IO／dispatch／密集頻寬）都已被量過並否定，
   剩下的那個（shape penalty）在 16.4% 的認證噪聲之內還量不出來」。
