二、讀源碼：sum_rows 其實是三層，不是「依序相加」

src/llama.cpp/ggml/src/ggml-metal/ggml-metal.metal:1721-1778

層行號行為
① 執行緒內:1748-1750跨步累加 for(i0=tpitg.x; i0<ne00; i0+=ntg.x)
② simdgroup 內:1752simd_sum(sumf)（蝴蝶，32 lane）

「依序相加」這個描述沒有一層對得上。樹形由 (ne00, ntg.x) 決定 ⇒ 寬度 k 不變時整棵樹與原本同形。

三、真正的關卡被換掉了

原本以為的關卡
IEEE
浮點非結合律 ⇒ 不可能
實際的關卡
圖建構
C 組輸出能否寫回原偏移

只差一件事

  • 若能：C 組寫回它在 routed order 的原始偏移 ⇒ src0 逐位元相同 ⇒ combine 逐位元相同 ⇒ M1 可達成。
  • 若只能 concat 成 [H | C]： routing 是交錯的不是分組的 ⇒ 位置序變 ⇒ 退回 D2 ⇒ 判死。

⛔ ggml 的 op 自備 dst，寫進既有 tensor 的偏移需要 view／scatter， 這份成本從來沒估過 —— 它是 D1 的第一個未知數。

三條會把人帶錯的坑

  • exit 2 ≠ M1 不過。 本項勢必新增 env；若進了 numerics-determining 子集， 每次都 exit 2，那不是回歸。
  • 基準是「移動」來的不是修好的。 09-27 v6→v7（825ec07d5）， 默認 M1 9/9 M2 9/9 M3 9/9；判據是引擎可重現。若要 --write-ref ⇒ 基準移動，須經 operator。
  • 鍵碰撞時 M1 不是判決。 gate 用 (step, token_idx, ctx_type) 當鍵； 09-28 已踩過「M1 1/14、coverage 8%」其實是鍵碰撞。

P1 為什麼不能跳：CGC_B_SCHEME（llama-context.cpp:3607-3634） 把缺席 expert 指到 e % ns ＝另一個 expert 的權重，不是 0 ⇒ 「缺席那一項 ≈ 0」這個補算前提現在不成立。

P2 兩個必踩的坑：ids 要用 slot index 不是 expert id； 有 CGC_DOWN_COMBINE 融合快路徑（llama-graph.cpp:2678-2765， :2764 直接 return）⇒ 補算必須考慮它。

六、on_fail：判死的話不准放寬護欄

若 P2 證明只能 concat ⇒ D1 退回 D2 ⇒ 判死。 然後：不得放寬 M1/M2/M3 護欄 —— 那是口徑移動不是修好。

判據：MTP 那次能走「口徑重定義」，是因為 n_rs_seq 讓計算份數本身改變 （gdn 30→60、conv_input 30→150）＝不同的輸出函數。 本項若只是加法順序不同，純屬實作選擇，不構成放寬理由。
