# 第一個「打桶」的實驗：`CGC_CB_N_MAIN` 的 ABBA（2026-09-26 14:24）

**問題（operator 14:06）**：「有開始消減串行的 gap/cb/fill 了嗎？」

**答案**：**在此之前沒有（今天 0 個可量測的消減）。這一支是第一個，而且它打出了
`−11.4%` decode step（`+12.8%` t/s）—— 但「是哪個桶」還沒定案，見 §5。**

---

## 1. 為什麼選 `CGC_CB_N_MAIN`

`n_main`（`ggml-metal-context.m ~:1141`）＝ **Metal 後端把一張圖切給「誰來編碼」的分界線**：
每次 `ggml_metal_graph_compute` 開 `n_cb + 1` 個 command buffer，**slot `n_cb`（最後一個）由
呼叫執行緒序列編碼**節點 `[0, n_main)`，其餘 `n_cb` 個由 worker 並行編碼剩下的。

```c
const int n_main = cgc_cb_nmain != NULL ? MAX(1, atoi(cgc_cb_nmain)) : MAX(64, 0.1*gf->n_nodes);
```

- **分段後每段 `N ≈ 99`** ⇒ `0.1 × 99 = 9.9` ⇒ **`MAX(64, 9.9) = 64` ⇒ 地板接管**
  ⇒ **65% 的節點由呼叫執行緒序列編碼**。
- 而 **64 是上游在 M1 Pro／M2 Ultra ＋ LLaMA 上「empirically determined」的**，不是這個 workload 的。
- 對應的桶：**`submit`（dispatch）與段起的 GPU 起始延遲（＝ gap 的一部分）**。
- **成本：0 重建、純 env**（`CGC_CB_N_MAIN` 已在 allowlist）。

**先前兩輪 sweep（皆髒窗、`attr=both`）都指向 `n_main=64` 是 `{16,32,64,128}` 裡最差**
（中位數 7.79 vs 9.67，+24%），但**不背書**（非單調 ＋ 盒子髒）。本支要在**桶**上確認。

## 4. 桶的分解（這才是重點）

```
Δtotal = −9.92 ms
  ├ wait    −6.80 ms  (69%)   ← 大頭
  ├ submit  −1.24 ms  (12%)
  ├ 餘項    −1.70 ms  (17%)
  └ cb      −0.19 ms  ( 2%)   ← 幾乎不動
```

- ✅ **不是打 `cb`**（−3.3%，在噪音內）。`cb` 是 gather，與編碼切分無關 —— 這與機制一致。
- ✅ **打到了 `submit`**（−23%）：分界線變小 ⇒ 呼叫執行緒更早提交首個 command buffer。**符合機制預期。**
- ⚠ **大頭在 `wait`（−6.80 ms）**，而 **`wait` 是複合量**（見 §5）。
- ⓘ **`fill` 不適用於這支 cell**：`CGC-HOOKSPLIT` 一行都沒印 ⇒ 這個配置下 hook 沒跑、fill 為 0。

## 5. ⛔ 還沒定案的一件事（必須說清楚）

`CGC-DECPROF` 的三個桶（wait／cb／submit）**由建構加總＝100% of step**，其中
**`wait` = eval-sync（CPU 等 GPU）** ⇒ 它**同時包含 GPU 真忙（union）與 GPU 空窗（gap）**。
本輪 `CGC-DECPROF topN:` 的 GPU 側欄位 `gpu=/union=/gap=` **全是 0.00** ——
因為那支量（`CGC_GPU_TIMING`，`ggml-backend.cpp:1860`）沒開。

⇒ **所以「−6.80 ms 是 gap 縮了、還是 union 縮了」目前分不出來。** 這兩者的意義完全相反：
- 若 **gap 縮** ⇒ **正是目標**（消掉 GPU 空窗，不碰 compute）。
- 若 **union 縮** ⇒ 只是 GPU 少做了事，**不是業績**。

**支持「是 gap」的結構性論據（但不是證明）**：`n_main` 只改**編碼切分**，不改節點集合 ——
**四臂的 `segs=41`／`layers=40` 完全相同**，節點本身逐一同構 ⇒ GPU 的**總工作量**不變，
差別只在 command buffer 的邊界。⇒ 這個 −11.4% 應歸因於**時間軸（何時開始算）**，不是**工作量**。
⚠ 但 command buffer 邊界**確實可以**改變 Metal 的排程效率 ⇒ **仍需 `CGC_GPU_TIMING` 才能定案。**

**下一個實驗（已備好、0 重建）**：同一組 ABBA ＋ `CGC_GPU_TIMING=1`
⇒ 直接把 `wait` 拆成 `union` 與 `gap`。判準：**`union` 不變而 `gap` 降** ⇒ 目標達成；
**`union` 降** ⇒ 這條線要重新定性。

## 11. 開跑前的核查（0 GPU，2026-09-26 14:5x）

一支腳本 ＋ 一個解析器，**沒花 GPU 就定下四件事**。產物：`Backup/phase_decomp/cbnmain_nm32/{run.sh,analyze.py}`。

### 11.1 ★ 「這一格還缺」是**實測**確認的，不是推理

最容易犯的錯是**重跑一個已經跑過的實驗**。`Backup/phase_decomp/cbnmain_buckets/` 的臂序
**與本輪完全相同**（`ctl64a → nm32a → nm32b → ctl64b`），看起來可以直接抄。

**逐字比對 stderr 後否決**：它的 env 是 `CGC_DECODE_PROFILE=1;CGC_HOOK_SPLIT=1`，
**沒有 `CGC_GPU_TIMING`** ⇒ 它的 `CGC-DECPROF` 行**短一截**：

```
buckets : CGC-DECPROF: step=1 ... ntok=2048
                                    ↑ 行到此為止
sweep3  : CGC-DECPROF: step=1 ... ntok=2048 | layer gpu_sum=13018.36 union_sum=7116.06 gap_sum=4520.87 ms
                                              ↑ 這一段是 CGC_GPU_TIMING 閘出來的
```

⇒ **`union_sum`/`gap_sum` 隨 `CGC_GPU_TIMING` 開關**，`buckets` 一個字節都沒有。
**這一格確實還缺；本輪是必要的。**
⚠ 反過來說：**若沒逐字比對，就會把 `buckets` 的「桶」数当成 union/gap 的证据** ——
那是一個**看起來有、實際沒有**的引用。

### 11.2 `skipped%` 必須做**整臂**閘（不是逐行）

`sweep3` 逐臂的 `skipped` 占比：

| 臂 | `n_main` | 乾淨/全部 | **skip%** | 判 |
|---|---:|---:|---:|:--|
| ctl64a | 64 | 83/97 | 13.4% | OK |
| nm16 | 16 | 95/97 | **0.0%** | OK |
| nm128 | 128 | 30/97 | **68.0%** | ⛔ STALE |
| ctl64b | 64 | 85/97 | 11.3% | OK |

門檻取 **20%**（`analyze.py: SKIP_MAX`）。超過 ⇒ 整臂 `union/gap/busy` **不參與判讀**。
理由不只是「說明書要求 `skipped==0`」——**更硬的是 `nm128` 連 `skipped==0` 的行都在說謊**
（`busy=2872 ms` 對 `wait=94.7 ms`，3034%，物理不可能）⇒ 逐行閘抓不到，**必須整臂丟**。

### 11.3 `nm32` 在**機制上**不會踩 `nm128` 那個坑（這是 0-GPU 的可行性證明）

`ggml-metal-context.m:1140-1175`：

```c
n_main    = CGC_CB_N_MAIN ? MAX(1, atoi(...)) : MAX(64, 0.1*n_nodes);
n_nodes_0 = MIN(n_main, n_nodes);      // 前 n_main 個節點由「呼叫執行緒」編碼
n_nodes_1 = n_nodes - n_nodes_0;       // 其餘分給 n_cb 個平行執行緒
```

⇒ **`n_main` 變大 ⇒ `n_nodes_1` 變小 ⇒ 某些平行執行緒分不到節點 ⇒ 空 command buffer ⇒ 無時間戳 ⇒ `skipped++`。**
**`nm128 > 預設 64` 正是這個方向；`nm32 < 64` 是反方向（`n_nodes_1` 更大）⇒ 結構上不產生空 buffer。**
這也解釋了 `nm16` 的 `skip% = 0.0%`（實測）—— 它是同方向的極端。

⇒ **`nm32` 的 GPU 側預期可讀（`skip% ≈ 0`）。** 若跑出來 `skip%` 很高，
**那是對本證明的反例，本身就是一個發現**（`analyze.py` 會在該臂打 `STALE`）。

### 11.4 判讀門檻必須用**控制臂漂移**，不能用固定值

`sweep3` 兩個控制臂（同 build、同臂、頭尾）的差：

| 量 | ctl64a | ctl64b | **Δ%** |
|---|---:|---:|---:|
| wait | 70.89 | 69.45 | −2.0% |
| union | 73.60 | 72.31 | −1.8% |
| **gap** | **15.05** | **16.41** | **+9.0%** |
| busy | 109.24 | 107.18 | −1.9% |
| tg | 10.19 | 11.13 | +9.2% |

⇒ **`gap` 的臂間噪聲底 ≈ ±9%**，是 `wait`/`union` 的 5 倍。
⇒ **任何 `gap` 的 Δ 沒有超過 ~9% 就不能說「命中目標」** —— 若沿用固定 ±5%，會把噪聲讀成訊號。
`analyze.py` 於是**逐量**算 `門檻 = max(控制臂漂移, 3%)`，並把未過檻的判為「在噪聲底內」。

### 11.5 先驗（`nm16` 的方向）與 `nm32` 的張力 —— 跑完要能解釋

§10.2 已量到 **`nm16`：union −8.6、gap +4.6、tg −26%**（餵不飽）。
而 **`nm32` 已知 tg +12.8%**。兩者方向**相反** ⇒ 若 `nm32` 的 `gap` **下降**，
則「`n_main` 有一個內部最優」成立（太小餵不飽、太大省不到）；若 `gap` 同樣上升，
則 `nm32` 的 +12.8% 必須由**別處**（`cb`/`submit`）解釋。**兩種結果都有資訊量。**

## 12. ★ `n_main=32` 的 union/gap 拆分（2026-09-26 22:16–22:26 重跑 —— 這一格補上了）

**臂序** `ctl64a(off) → nm32a(on) → nm32b(on) → ctl64b(off)`，全帶
`CGC_DECODE_PROFILE=1;CGC_HOOK_SPLIT=1;CGC_GPU_TIMING=1`。機器 **21:37:49 重啟**過 ⇒ 真空窗
（起跑時 `thermal=0`、壓縮器 `QUIET`、窗口門 3/3 連續乾淨）。

| 臂 | `n_main` | clean/all | skip% | union | gap | busy | fill(µs/call) | tpot | tg | pp |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| ctl64a | 64 | 73/97 | 23.7% | ⛔STALE | ⛔ | ⛔ | 155.4 | 81.19 | 10.17 | 271.0 |
| **nm32a** | **32** | **95/97** | **0.0%** | **59.41** | **16.87** | **59.26** | 217.5 | 76.32 | 10.02 | 285.8 |
| **nm32b** | **32** | 9/11 | 0.0% | **59.81** | **17.10** | **59.64** | 55.8 | 84.81 | — | 267.5 |

（單位 ms，median；`fill` = `ensure_batch`，取最後窗口增量。`clean/all`：乾淨行/全部行。）

### 12.1 ★★ 可引用的結論：`union` **降**、`gap` **升**（與 §11.5 的假設相反）

- **`union`：`32` 兩次獨立復現 `59.41` / `59.81`（散佈 0.7%）** vs 控制 `69.66`（ctl64b，3.1% skip ⇒ 可信）
  ⇒ **−14.7%**。**效應量（−15%）遠大於處理臂內部散佈（0.7%）** ⇒ 這是真的。
- **`gap`：`32` 為 `16.87` / `17.10`（散佈 1.4%）** vs 控制 **`13.61`** ⇒ **+24%**。
- **`busy`：`59.5` vs `97.5` ⇒ −39%**（每個 buffer 時長總和下降 ⇒ 切片/並行度變了）。
- **⇒ 「`−11.4%` 是消掉 `gap`」的假設被推翻**：`n_main=32` **把 GPU 忙窗縮小了、空窗反而變大**
  —— 與 sweep3 的 `nm16`（§10.2）**同方向**，只是幅度較小（`nm16` 是 −8.6 / +4.6）。
- ⚠ **這也意味著 `n_main` 的收益（若存在）不來自 `gap`** ⇒ 若要拿它當槓桿，得先解釋它**靠什麼**贏。

### 12.1b ★★ 新發現：`busy/union` 比 **1.41 → 1.00** ⇒ `n_main=32` **消除了 buffer 間的並行重疊**

- `busy` = Σ 每個 buffer 的 `(GPUEndTime−GPUStartTime)`；`union` = 這些 buffer 的**聯集 span**。
  兩者之比 ⇒ **同一步內 GPU 上的並行重疊程度**。
- **控制臂（`n_main=64`）：`busy/union` = 100.09 / 71.09 = `1.41`** ⇒ buffer 間**有 41% 的重疊**
  （`n_cb+1` 個 command buffer 確實在並行跑）。
- **`n_main=32`：`busy/union` = 59.45 / 59.61 = `1.00`** ⇒ **重疊消失** ⇒ GPU 上的 buffer 變成**幾乎串行**。
- **⇒ `n_main` 不只改「誰來編碼」，它改變了 GPU 端的並行結構。** 這解釋了 `busy` 為何掉 40%
  而 `union` 只掉 16%：**掉的 24 個百分點是「重疊」本身**。
- ⚠ **但 `tpot` 沒有跟著降**：處理臂 `76.32`/`84.81` vs 控制 `81.19`/`74.36`。
  **`union` 少掉的 ~11.5 ms 被 `gap` 多出來的 ~2.4 ms 加上臂間噪聲吃掉了**
  ⇒ **淨效應小於 `tpot` 的臂間散佈（~10%，見 §12.2）** ⇒ 這就是為什麼 `tg` 看不出差異。
- ⇒ **對本線目標（消 gap/wait/cb/fill）的判斷**：`n_main=32` **不是**一個 gap 槓桿，
  它是**用「段間空窗」換「段內並行」** —— 總時間守恆。**若要它變成收益，得讓換掉的並行不被空窗吃掉。**

### 12.2 ⛔ 不可引用：`tpot` / `tg`（窗口漂移 15.5%）

控制臂自身漂移 **`ctl64a` 10.17 → `ctl64b` 11.75 t/s = +15.5%**，**遠超 ±9% 的噪聲底**（§11.4）
⇒ 窗口在四臂期間**單調改善**（越跑越快）⇒ **絕對 t/s 不可比**。
本次 `nm32a`(10.02) 反而低於 `ctl64b`(11.75)，**但這是漂移造成的，不能推翻 buckets 的 +12.8%**
（buckets 那輪控制臂 9.94/10.21，與本輪 `ctl64a` 10.17 接近 ⇒ 是本輪的 `ctl64b` 偏高）。

### 12.3 ⛔ `nm32b` OOM：這是**結構性**的，不是偶發

```
rc=-6  ggml_abort；ggml_metal_synchronize → llama_context::synchronize → test_gen
swap 4394 → 12607 MiB；wired=12428 MiB；min_free=14.14 MiB
```

**`min_free ≈ 14 MiB` 與上一輪 `ctl64b` 的 OOM（14.09）幾乎相同** ⇒ 那是 macOS 的硬底。
**機制**：**每跑一臂 swap 漲 ~8 GB，而 swap 存量不會自動回落**（見 `MEMORY_HYGIENE.md`
「`swap_used` 是錯的軸」—— 它**不會掉回去**）⇒ **連跑四臂必累積到 OOM**。
❗ **「一支腳本跑完四臂」在 16 GB 上是不可靠的**，這是本輪最貴的教訓。
（`purge` 是已知解法，但本機 `sudo -n purge` 回 `a password is required` ⇒ 無法自動化。）

### 12.4 下一步（若還要**可比的 t/s**）

1. 拆成**兩支腳本**（`off` 一支、`on` 一支），中間 `purge` 或重啟；
2. 或只跑**相鄰一對**（`off → on`），用**臂間配對**判讀（少一臂 ⇒ 少一次 swap 累積）；
3. **GPU 三桶（`union`/`gap`/`busy`）不受此事影響** —— 它們是**步內**測量，
   且處理臂兩次復現極好（散佈 0.7%/1.4%）⇒ **§12.1 的結論已經成立**。
