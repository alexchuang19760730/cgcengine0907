2. 閘門鏈（機制）

每一步都是一手可查的：

  1. CGC_SERVER_LAYER_CAPS=40-40:16 ⇒ 第 40 層 16 槽 ⇒ llama_expert_cache_usable_slots = 16 - 1 = 15（扣掉保留的 ZERO 槽）。
  2. min_usable = min(有池層的 usable) = 15（llama-context.cpp:344-361）。
  3. cgc_decode_width = min(cap=8, floor(15/8)) = 1（llama-cgc-phase.h）。
  4. MTP verify 批 n_tokens = 2 > 1 ⇒ cgc_select_graph_phase(2,1) = PREFILL （llama-cgc-phase.h:141）。
  5. ⇒ 走 llama-context.cpp:8073 的 if (!cgc_is_decode_graph(...)) 分支： 整層 256 專家 slab（CGC_PREFILL_STREAM=1 已 armed），每層同步等一次雙緩衝填充。
  6. 該分支在 :8334 return ⇒ fast path 與池路徑在 verify 步完全不執行。
日誌直接有證：slab=110.00 MiB filled=115343360 bytes db=1（db=1 ＝ 雙緩衝）。 算術自洽：110 MiB × 41 層 ≈ 4.5 GB/步；cb ≈ 99 ms/層 × 41 ≈ 4.1 s/步。 這條成本與批寬無關（永遠讀全部 256 專家），正好解釋三個觀測：cb(ntok=2) ≈ cb(ntok=512)、 gpu_sum 只佔 8%、gap_sum ≈ total。而 draft 步（ntok=1 ≤ width=1）是 decode 圖 ⇒ 走池路徑 ⇒ 健康（cb 5.7 ms／步）。

本輪沒有跑「儀器開啟」的 D5。理由：該臂會多出兩個不被 DIAGNOSTIC_KEYS 收錄的 env （ENV.CGC_FASTPATH_SPLIT: ref='<absent>' now='1'）⇒ 必然 comparable=False， 那時的 9/9 依 gate 自己的說明只是「印出來看的」，沒有判決力。 依 skill 的判準，只有「休眠態 comparable=True」那一趟有判決力，本輪已取得（§7.2）。
