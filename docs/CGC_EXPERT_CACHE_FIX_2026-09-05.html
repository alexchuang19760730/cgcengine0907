二、根因分析

2.1 Expert Cache 0000 Bug

症狀：ngl=99 + expert cache + MTP 時，模型輸出 00000000000000000000000000000000 或 !!!!!!

根因：

  1. Expert cache pool capacity 計算：budget / (41_layers × per_slot) = 87 slots
  2. 但模型有 256 experts（Qwen3.6-35B-A3B MoE）
  3. Pool 將 ne[2] 從 256 縮減到 87 → 金屬 buffer 只有 87 個 slot
  4. 當 gate routing 到 expert ≥ 87 時，映射到 slot 0（零權重）
  5. Layer 2+ gate 看到退化的 hidden state → uniform logits → sequential IDs [0,1,2,3,4,5,6,7]
  6. 模型輸出垃圾

關鍵證據（debug log）：

Layer 0: ids=[181 208 254 112 6 81 238 203]  ✅ diverse routing
Layer 1: ids=[19 170 214 167 45 246 125 149]  ✅ diverse routing
Layer 2+: ids=[0 1 2 3 4 5 6 7]               ❌ sequential default

2.2 Embedded GGUF Template 問題

症狀：Code generation 輸出 <|user|> / <|assistant|> 原始標籤

根因：run_n30cache.sh 默認使用自定義 Nail-Qwen3.6-Minimal-Chat.jinja 模板，該模板使用舊格式 <|user|>，但模型期望 ChatML 格式 <|im_start|>

三、修復方案

3.1 Expert Cache 修復（C++ 層）

策略：Resident Passthrough（§7.3.5 設計文檔）

組件修改文件
Model Loaderexpert_cache_skip_load=true 時，expert tensors 留在 CPU，ne[2]=256（不縮減）llama-model-loader.cpp
Graph Buildskip_load=true 時，跳過 pool repointing（不將 FFN 權重指向 pool regions）llama-context.cpp
Eval Hookskip_load=true 時，強制 identity remap（real expert IDs 0..255），跳過 pool pathllama-context.cpp
效果：Identity remap 讓 Metal 從原始 full-size tensor 讀取（ne[2]=256），所有 256 個 experts 都可用。Gate routing 正確（diverse IDs），語意品質完全恢復。

五、速度限制分析

⚠️ 當前速度 5.5 t/s，未達 25+ t/s 目標。

根因：Resident Passthrough 將 expert tensors 放在 CPU（ne[2]=256），Metal 從 CPU 讀取。

因素影響說明
Expert tensors on CPU主要瓶頸256 experts × 41 layers 在 CPU 上，Metal 通過 unified memory 讀取
MTP 開銷次要MTP draft context 佔用 ~2GB GPU 記憶體
16GB Mac 限制根本限制13GB 模型 + MTP + KV cache → 無法將所有 expert tensors 放到 GPU

達到 25+ t/s 的條件：

  1. Pool path 修復：需要將 pool capacity 提升到 256 slots（需要 ~19GB budget），在 16GB Mac 上 OOM
  2. 32GB+ Mac：足夠記憶體容納所有 expert tensors 在 GPU 上
  3. 更小的模型：減少 expert 數量或量化精度
