乾淨窗 ABBA 嘗試：判死未達成，而且本輪不產出可引用的 t/s

判死未達成 3/4 趟 memory gate UNUSABLE 第二區塊起跑前被拒 起跑窗四趟皆乾淨 0 個可引用的 t/s 維持不改預設值

一句話：把「趟間睡 40 秒」改成「輪詢到起跑 thermal=NOMINAL ＋ 壓縮機安靜」之後，噪音確實掉了一個量級（處理臂兩趟 tg 差 17.2% → 1.18%）， 但 harness 自己的記憶體閘把 3/4 趟判成 UNUSABLE（swap 峰值成長 756–1446 MiB vs 預算 512 MiB），而補跑的第二區塊（BAAB）在起跑前就被拒（free 4593 MiB < 地板 5000 MiB）。 ⇒ 本輪沒有產出可引用的臂比較，判死未達成。

1. 這一輪實際改了什麼

上一輪（abba1..4）：run_arm A; sleep 40; run_arm B; sleep 40; run_arm B; sleep 40; run_arm A
本輪（clean1..4）：每一趟起跑前輪詢到「真乾淨」才跑：
    thermalpressure == 0  且  compressor_pressure.py --require  且  8080/llama 行程空
★ 環境坑（這一次才定位到正確歸因）：背景行程的 sys.path 看不到系統 site-packages。 同一支 /opt/homebrew/bin/python3（3.14.6），前景 import yaml 印 6.0.3， 背景跑同一行噴 ModuleNotFoundError ⇒ 第一版腳本四趟在 36 秒內全廢 （rc=1，log 只有一行「需要 PyYAML」）。修法： PYTHONPATH=/opt/homebrew/lib/python3.14/site-packages; export PYTHONPATH。 ⚠ 之前把這件事記成「managed 3.13 沒裝 PyYAML、要換 interpreter」是錯誤歸因 —— 變因是前景／背景。

4. 兩個比這一次量測更有價值的發現

4.1 「全程 thermal=NOMINAL」在這個 cell 上做不到

即使起跑 NOMINAL、壓縮機安靜，趟內 HEAVY 採樣仍佔 44–55%，四趟 worst 全是 HEAVY：

趟NOMINALMODERATEHEAVYlaunch → worst

clean2_nm32a681566NOMINAL → HEAVY
clean3_nm32b631572NOMINAL → HEAVY
clean4_ctl64b651671NOMINAL → HEAVY
⇒ 可操作的「乾淨窗」定義要換成四條，而不是「全程 NOMINAL」：
① 起跑 thermal=NOMINAL；② 起跑 compressor QUIET； ③ 趟內 tg 標準差小（本輪 ≤ 0.64 vs 髒窗 1.1–1.5）；④ 過 harness 的 memory gate（本輪 3/4 沒過）。

4.2 16 GB 盒子上，這個 cell 一個場次大概只能連跑 2–4 趟

第 1 趟起跑 swap 4066 MiB ⇒ 第 5 趟起跑 free 只剩 4593 MiB（< 5000 地板）⇒ 拒跑。 每趟 wired 成長約 5.8 GB、swap 峰值成長 570–1446 MiB，不會在趟間歸還 ⇒ 8 趟的 ABBA 在單一場次內不可行，除非先關掉 GB 級 app 或重開機。 （盒子自己點名：WorkBuddy Helper (Renderer) 2105 MiB、Freebuff 562 MiB、Electron×2 763 MiB。）

⚠ scripts/check/memory_pressure.py 的 mtime 是 16:18 —— 別條線在我跑的同時正在改這個閘（git diff +494 行）⇒ 512／5000 這兩個門檻是 本輪當下的值，可能再動。上一輪（15:03）的 log 裡完全沒有 memory gate 那一節 ⇒ 兩輪放行標準不同，不能說「上一輪也 UNUSABLE」。

8. 判定與處置

項目結果
起跑乾淨窗（launch NOMINAL ＋ compressor QUIET）✅ 四趟都做到
「全程 NOMINAL」❌ 做不到（趟內 HEAVY 44–55%）
memory gate（臂可用性）❌ 3/4 UNUSABLE；第二區塊起跑前被拒
配對符號一致✅ 首次一致（+7.11% / +0.70%）
兩對皆 ≥3%❌ 只有一對
判死❌ 未達成
09-26 的 +12.8% 仍然未復現（本輪 raw +4.7%、對齊後 +2.5~3.3%，都不到一半）。 但「完全沒效應」也沒有被證成 —— 本輪是第一次兩對同號。 真正的結論是：這顆 cell 在目前這個盒子狀態下量不出判死所需的證據。

8.1 處置

  1. 維持不改 scripts/run_server.sh 的預設值（CGC_CB_N_MAIN 維持 unset）。
  2. 本輪 t/s 不進任何結論（3/4 UNUSABLE）；§5 的對齊值只當提示。
  3. 要判死：先讓盒子安靜（關掉 GB 級 app 或重開機），再一次跑滿 8 趟（ABBA ＋ BAAB， 兩個區塊都要過 memory gate）。⚠ 兩個區塊之間要讓盒子回到 free ≥ 5000 MiB，否則第二區塊會被拒跑。
  4. 若仍拿不到 ⇒ 依 on_fail 登記為「本盒子無法判死」，而不是「效應為零」。

9. 誠實邊界

  • 不主張 n_main=32 有或沒有增益 —— 本輪的臂比較被自己的閘判為不可用。
  • 不主張任何 TPOT 分解或分段拆解（§6、§7 全標「本輪未量測」）。
  • 不主張 wait 的縮減來自 gap。
  • §5 的 swap 對齊是 4 個點的迴歸假設（32 側自身斜率還與 64 側反號），不是量測。
  • 未跑：DECPROF、GPU timing、{16,64,128} 掃描、8 趟完整 ABBA。
  • 技術子目標：本槓桿既不動 41 段提交的同步（S）、也不動 MTP（M）⇒ 不適用。
