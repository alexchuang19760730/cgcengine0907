# 機會地圖：除了「消串列」，還有什麼（2026-09-26）

> 起因：operator 問「把串列消減只剩 compute 這條線 —— 除了這個就沒機會了嗎」。
> 本篇是**結帳重排**，跑 0 GPU、0 建置。所有引用都有出處。

---

## 0. 先修正提問本身的框

目標函數寫的是「把 **gap／wait／cb／fill** 最大程度消除」。而這四個桶都住在同一句話裡：

```
step 的牆鐘 ≈ 157.8 ms  =  GPU 真忙 113.4（71.8%） + GPU 空窗 44.4（28.2%）
                          ↑ 這被當成常數                     ↑ 唯一的靶
```

**⇒ 這個框把兩個最大的數劃到範圍外：**
1. **`union` 113.4 ms（72% 的 step）** —— 被當成「compute 地板」，但它的**佔用率**只有峰值頻寬的 ~11%。
2. **`E`（accept／mean len）** —— `t/s = E / step_time`。攻擊 `E` 與攻擊 `step_time`
   **在數學上等價**，而它完全不在這張表上。

⇒ 所以「除了消串列就沒機會」**只在「union 是常數」這個前提下成立**。而那個前提不是事實，是**一個假設**。

## 2. ★ 三條沒被窮盡的軸（依「上界 × 可驗證性 × 成本」排）

### 軸 D：`E`（accept／mean len）—— **完全不在表上，而且現在第一次可量**
- `t/s = E / step_time` 是恆等式。而 `E` 現在是 **1.70**（`MTP_CTX_REPRODUCIBLE` §2，五次 launch 同一字串）。
  切換前那一支（不同軌跡，不可直接比）報的是 **`mean len 2.02`**。
- **為什麼現在才可量**：同一份文件證明 `E` 在 server carrier 上是**配置的函數、不是抽樣**
  （五次 launch 完全同一條字串）⇒ 這是全專案第一次能可靠地量它。
- **掛著的矛盾**：`ASL 3.117 vs E 1.62` 未裁定（`MEMORY_PERF` MTP 節）⇒ 這個量本身可能有口徑問題。
- **成本**：0 重建、兩支臂（pre/post）。
- **上界**：若 `E` 能回到 2.02 ⇒ **+19%**。而且它不碰 kernel、不碰 leaf、不碰預測。

### 軸 W：K5（`L2` 的判 0 依據）—— **唯一「機制判定」擋住 +30~38% 的地方**
- L2 = 0 的**唯一**依據是「K5 = (C)：elementwise 節點撐不滿 grid，所以那 1014 節點 × 34.8 µs 拿不到」。
- 這是**機制性判定**（不是「量測未分離」）⇒ 依本專案紀律，機制判定要能指到一行代碼或一個算式。
- **一條反向線索**：`CGC_GLU_FUSED_DOWN=1` **已經在生產預設裡**（實測 `prefill250` 的解析後環境）——
  說明「融合 elementwise」**確實拿到了一部分**。若 elementwise 全體都撐不滿 grid，
  那 GLU 融合是怎麼過的？這條線索值得對一次。
- **成本**：查 `docs/` 裡 K5 的判 0 依據 ＋ 可能需要一支量測。

### 軸 R：ρ／prebind（`L3`）—— 判 0，而**我今天獨立算出了它為什麼該判 0**
- 09-25 撤回的理由與我今天從代碼算出的**同向但不同因**：
  - 複核的理由：機制＋量測（`L3` 撤回）。
  - **我今天算出的因**：文件說「視窗根本綁不住」的依據是
    `cb=42.04 時每層需求 1.051 ms < 最悲觀視窗 1.30 ms`，**而那個 1.051 是 ntok=1 的數**。
    交付 cell 是 ntok=4，每次 hook 的真實 **union 從 ~8 變 19.0~19.8**（實測）
    ⇒ **每層需求 ≈ 2.5 ms > 視窗 1.31~2.27 ms ⇒ 綁不住。**
- ⇒ **ρ 若要救，要救的是「窗口」，不是「insert」。** 而 insert 只是它的入場費。

## 5. 軸 W 複核結果（2026-09-26 11:0x，讀代碼後 —— **上一節寫錯了，這是更正**）

### 5.1 我上一節寫錯了：K5=(C) 不是「機制判定」，是「**儀器判定**」

`docs/K5_VERDICT_2026-09-21.md` §0 原文：

> **(C) 成立：那個 45.6 µs 是儀器的代數恆等式，不是物理。**
> K5 建立在它上面的「上界 30–38%」**全部作廢**，L2 歸零。

依據是 `ggml-backend.cpp:2421` 的 `nsop_wns[q] += dur * ocnt[q] / owork;` ——
把每個 command buffer 的時長**按節點數線性分攤** ⇒ 是代數恆等式。三條佐證：
- `uni` 欄全是 `-1.000`（從來沒有單 op 的 buffer ⇒ 無從做精確除法）；
- Σ`wcntw` 只覆蓋 87–93%；
- 同一個 step 裡 `CLAMP`(39)、`DIV`(39)、`GLU`(78)、`SUM_ROWS`(39)、`MUL_MAT_ID`(117)
  的 µs/node **恰好都是 52.05** —— 節點數差 3 倍、運算完全不同，小數點後兩位相同。

⇒ **L2 的死因是「量它的儀器是假的」。這與今天一路在修的「儀器說謊」是同一類，而且它是對的。**
⇒ 我上一節把它寫成「機制判定（elementwise 撐不滿 grid）」**是錯的** ——
判決 §4 明說 **(A)/(B) ⬜ 未定**（M 掃描在同形性下分不出來），不是判成 (A)。

### 5.2 ★ 但判決書的下游結論有兩處與**現樹代碼**不符

**(1)「64 是硬湊、拆不開」不成立。** 判決引用 `ggml-metal-context.m:1099` 的
`n_main = MAX(64, 0.1×n_nodes)`，並說 64 是硬編碼。**現樹在 `:1141`**：

```cpp
// [CGC 2026-09-18] CGC_CB_N_MAIN is a MEASUREMENT-ONLY override of the MAX(64, ...) floor.
// ... Unset => upstream behaviour, byte for byte.
const char * cgc_cb_nmain = getenv("CGC_CB_N_MAIN");
const int n_main = cgc_cb_nmain != NULL && cgc_cb_nmain[0] != '\0'
                 ? MAX(1, atoi(cgc_cb_nmain))
                 : MAX(64, 0.1*gf->n_nodes);
```

⇒ **可 env 覆寫、0 重建。** 而全 repo 只有 `docs/GPU_NODE_ATTRIBUTION_20260918_0126.html`
提到它，而且是被當**量測配置**用（`CGC_CB_N_MAIN=1 ＋ CGC_SERVER_N_CB=16 ⇒ 2–7 節點的切片`）
⇒ **從來沒被當效能旋鈕掃過。**

**(2)「61.3% 沒有槓桿」這個解讀漏了一半。** 判決把 64-node buffer 的內容數出來
（`ffn_moe_` 25.9%、`cache` 9.6%、…）⇒ 結論是「裡面是 MoE 真實大計算，拆開不會省」。
**但它沒回答另一半：那些節點是「由主執行緒序列編碼」的。** `:1151-1153` 自述：

> *the first `n_nodes_0` are encoded and submitted for processing **directly by the calling thread**
> while these nodes are processing, we start `n_cb` threads to enqueue the rest of the nodes*

### 5.3 ★ 算術核對（用既有的數，0 GPU）

- `segs=41`、trunk `n_nodes_all=4076` ⇒ 每段 **≈ 99 節點**
- `0.1 × 99 = 9.9` ⇒ `MAX(64, 9.9) = **64**` ⇒ **每段 64 of ~99 個節點（65%）由主執行緒序列編碼**
- 對位驗證：K5 量到「nodes/buffer = **64** 的 buffer 每步 **44.5** 個」——**正好對上 `segs=40~41`** ✓
  （worker 側「nodes/buffer = 5：214.6 個/步」≈ 41 × 8 = 328 的量級 ✓）

### 5.4 所以軸 W 的正確形狀

| | |
|---|---|
| **L2（+30~38%）** | ⛔ **確實死了** —— 它的儀器是假的（代數恆等式） |
| **但死的不是「打包參數」** | `CGC_CB_N_MAIN` 可覆寫、0 重建、**從未被當效能旋鈕掃過** |
| **機制假設** | 主執行緒**序列**編碼每段 65% 的節點；`n_main` 大 ⇒ 首個 submit 更晚；`n_main` 小 ⇒ GPU 前置工作少、worker 更早接手。**最優值隨工作負載變，而 64 是上游在 M1 Pro／M2 Ultra ＋ LLaMA 上調的，不是這個 workload 上的。** |
| **對應的桶** | `submit`（10.8 ms/step）與段起的 GPU 起始延遲 |
| **成本** | **一支 sweep（0 重建）**：`CGC_CB_N_MAIN ∈ {16, 32, 64, 128}`，`CGC_N_CB` 固定 8 |
| **反向線索** | `n_cb=8` 而**上游註解說「optimal values for n_cb are 1 or 2」**（`:1156`）⇒ 本專案已離上游很遠，說明 `(n_main, n_cb)` 這個二維**確實需要按本 workload 重新定** |

⚠ **不宣稱一定有效**：這是一個**有機制動機、成本極低的未探索旋鈕**，不是已知的 +X%。
