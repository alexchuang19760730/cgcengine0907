0. 一頁摘要

能引用的一句話：prod-new 的 MTP off 在今天這種超訂盒況（swap 存量 7.9 GB、壓縮機安靜）下量到 tg 11.46；MTP on 只有在「正確武裝」時才存在讀數，而它目前的經濟學是 S = 0.79–0.92 ⇒ k* = 1， 即比 off 慢。要讓 on 划算，缺的是 accept（k 的攤薄來源），不是把 k 開大。

三個不能忘的陷阱：

① CGC_SERVER_MTP=1 不是投機——它只是一個 env 區塊；spec 要用 --spec-type draft-mtp 才武裝。09-26 的三筆「MTP on」讀數（10.45 / 11.21 / 275.28）因此全部作廢。

② swap 存量 不是「盒子髒」的判準；決定者是壓縮機流量。舊閘在 09-26 拒跑了乾淨盒 （存量 7833 > 1024），卻放行了壓縮機忙的盒（存量 4.5 GB、量到 8.31 t/s）。

③ 12.57 是已武裝的交付 cell（MTP on），不是 MTP off 的基準；off 的生產讀數是 11.03 / 11.79 / 12.20。

2. MTP on/off：狀態、陷阱與正確指令

2.1 陷阱：env ≠ 投機（09-26 最新落地的一條閘）

09-26 有三筆讀數被當成「MTP on」引用，實際上零投機：產物 spec_type: null、印出的 cmd 沒有 --spec-type、SPECDBG round: 0 行，而 CGC-WARM verify 在 on/off 兩臂都印 24 行 （所以它從來不是投機的證據）。現在 llama_bench_matrix 在任何一臂啟動前就會拒跑這種組合。

$ python3 scripts/check/llama_bench_matrix.py --arms "prod-new:CGC_SERVER_MTP=1" --dry-run
REFUSED: arm env CGC_SERVER_MTP=1 but no --spec-type ⇒ this arm would measure an
unarmed cell and be read as "MTP on". Add --spec-type draft-mtp.

2.2 正確的 on/off 指令

# MTP off（prod-new 原樣）
python3 scripts/check/harness.py bench --arm prod-new \
  --prompt 2048 --gen 128 --depths 512 --reps 3 --ctx-size 0 --warm-skip 64 \
  --workdir /tmp/pn_off --json /tmp/pn_off/result.json

# MTP on（k=3；同一 cell，只增 spec 兩個旗標）
python3 scripts/check/harness.py bench --arm "prod-new:CGC_SERVER_MTP=1" \
  --spec-type draft-mtp --spec-draft-n-max 3 \
  --prompt 2048 --gen 128 --depths 512 --reps 3 --ctx-size 0 --warm-skip 64 \
  --workdir /tmp/pn_on --json /tmp/pn_on/result.json

驗收（跑前寫死）：產物 spec_type == "draft-mtp"、spec_draft_n_max == k、stderr 出現 SPECDBG round:（k 的見證）且 warm_skip_applied == True。任一項不成立，該讀數作廢。

2.3 為什麼 on 現在比 off 慢

spec 的損益是 S = E / (1 + m·k_eff)：每個 draft token 都要把主模型的 expert 位元再讀一次， 而 MoE gather 家族在本機形狀下結構性攤不薄（T=2 就是 T=1 的兩倍）。已測得 S = 0.79–0.92、 k* = 1（accept 0.47–0.60）⇒ 開 k=3 只是花錢買不到 token。

量今天的值來源／口徑
verify 每 token 邊際51 ms/token（回合內）k-sweep，回合固定成本 vs 邊際
MoE gather 的每 token 邊際+7.91 ms/token（extra_over_first 0.977）形狀隔離探針（256 experts × top-8 × 40 層）
k 的最優值1S = 0.79–0.92 ⇒ S>1 才值得加寬
要划算所需的 accept≥ 0.80同上前提下的敏感度

4. harness 量測框架

① 入口（一個前門）
harness.py：bench（量測）/ show（盒況看板）/ verify（雙輪驗證 + HTML）/ selftest。所有 wrapper（prod_matrix.py、commit_bench.py、arm_two_pass.py…） 都 delegate 到同一條路徑，量測邏輯不複製。
② 解析與 cell 契約
llama_bench_matrix.py：把 profile 名解析成完整 env（resolve()）； 用 _base_gate 比對 base 是否被改動、用 _swap_arm_gate 檢查 P0/P1/P2/B_SCHEME 是否在場； 用 mtp_without_spec 拒絕「MTP=1 但沒 spec」的臂；逐項驗 cell 維度（14 項）；印出 profile/env/counters， 把每臂的 stderr 存成 <stem>.stderr.log（CGC-MTP-PERF、SPECDBG 等見證都在那裡）。
③ 窗口（同一個探針，所有啟動器共用）
server_window.py：quiet()/require()/record()/require_first()/provenance() + audit（誰是啟動器、有沒有 gated）+ audit-products（產物有沒有窗口區塊與側車）。 四個 term：port／外來 llama 行程／可回收記憶體／壓縮機安靜度（compressor_pressure.py）。 thermal_pressure.py 提供 wait_nominal()；memory_pressure.py 提供下面的標籤。
④ 產物與出處
每臂的 JSON 帶：build_commit、cell 區塊、cache（hit/miss/reads）、 thermal（逐 0.5 s 取樣）、memory（逐 1 s：swap/free/wired）、attribution （thermal 最壞 + swap growth + wired growth）。報告類產物需有對應 JSON 側車，否則 commit 閘擋下。
⑤ 閘與回歸（commit 前必跑）
commit_gates.py：commit 必須有 Gates 區塊 gate_consistency.py：規格 vs 實作的漂移 window_gate.py：ungated 啟動器只能減少 m123_oracle_gate.py：M1/M2/M3 + DIAGNOSTIC_KEYS mtp_ctx_repro_certify.py：MTP 列的可重現性憑證 各工具 --selftest（含「必須紅」fixture）

4.1 一次量測的生命週期

  1. 窗口：_box_gate → thermal 冷卻到 NOMINAL → [compressor]（決定者，busy ⇒ 拒跑，除非 CGC_WINDOW_OVERRIDE=1）→ [swap-stock]（標籤）。
  2. 臂閘：base 沒被偷改 + P0/P1/P2/B_SCHEME 在場 + MTP 有 spec（或試圖武裝）。
  3. 解析：profile → env；cell 維度逐項比對。
  4. 啟動：llama-bench（--warm-skip 64），stderr 全存。
  5. 取樣：thermal 0.5 s、memory 1 s、必要時 CGC-DECPROF 逐層。
  6. 產物：JSON + 側車 + 窗口 provenance（class: clean / busy-then-cleared / busy-overridden / unknown）。
  7. 判定：散度、thermal、swap growth 三者寫進 attribution；不是判決的欄位不得長得像判決。
  8. commit 閘：Gates 區塊 + 漂移檢查 + ungated 只能下降。
